# A1 Spike — `UIContentUnavailableConfiguration` retry-button accessibilityIdentifier hook

**Spike target (RESEARCH §Assumption A1 / §Open Question 1):** can the iOS 17
`UIContentUnavailableConfiguration` carry a settable `accessibilityIdentifier` on
its retry-button without relying on a post-render `recursiveSubviews` walk?

**Why this matters:** UI-SPEC §Accessibility Identifiers lines 202–210 lock
`"loads-list.error-state.retry"` as the XCUITest probe target. The Plan 04
5-role UI smoke test will tap that identifier; if we cannot attach it
deterministically, the locked test surface breaks.

## Surface inventory (iOS 17 SDK, verified against `UIKit` headers in Xcode 26.4)

`UIContentUnavailableConfiguration.empty()` returns a value type with:

```swift
public struct UIContentUnavailableConfiguration: …, UIContentConfiguration {
    public var image: UIImage?
    public var imageProperties: ImageProperties
    public var text: String?
    public var textProperties: TextProperties
    public var secondaryText: String?
    public var secondaryTextProperties: TextProperties
    public var button: UIButton.Configuration?
    public var buttonProperties: ButtonProperties
    public var secondaryButton: UIButton.Configuration?
    public var secondaryButtonProperties: ButtonProperties
    // … layout/background properties …
}
```

`ButtonProperties` exposes:

- `var title: String?`
- `var image: UIImage?`
- `var primaryAction: UIAction?`
- `var menu: UIMenu?`
- `var role: UIButton.Role`
- (… and a handful of layout knobs)

**`ButtonProperties` does NOT expose `accessibilityIdentifier`** — it is a
purely-visual configuration container. Neither does `UIButton.Configuration`
itself: `accessibilityIdentifier` is an `NSObject` property, not a
`UIButton.Configuration` property, so configuration-driven buttons inherit it
from the rendered `UIButton` instance only.

`UIContentUnavailableView` (the host view UIKit instantiates when the
configuration is applied) is `internal` to UIKit — there is no public API to
query its retry button by tag, role, or property path. The only available hook
is a post-render recursive subview walk for the first `UIButton` descendant of
`view`'s `contentUnavailableConfiguration` host.

## Verdict

VERDICT B — hand-rolled required

No clean accessibilityIdentifier hook exists on the iOS 17
`UIContentUnavailableConfiguration` surface. The only available mechanism is a
post-render `recursiveSubviews` walk to locate the auto-instantiated
`UIButton` and set `accessibilityIdentifier = "loads-list.error-state.retry"`
on it after `setNeedsUpdateContentUnavailableConfiguration()`. That mechanism
is fragile across iOS minor versions: the internal view hierarchy of
`UIContentUnavailableView` is not part of UIKit's public contract and could
reshape between iOS 17.x and iOS 18+ (Apple has reshuffled
`UICollectionViewListCell`'s internal hierarchy before for similar visual
configurations). The Plan 04 5-role XCUITest would silently degrade to a
"button not found" failure on the first reshape — exactly the regression a
locked accessibilityIdentifier is meant to prevent.

**Task 3 implements `.error` via a hand-rolled `UIStackView` background view**
under `LoadListViewController.errorStateView`. The empty state still uses
`UIContentUnavailableConfiguration.empty()` (no button, no host-view-walk
ambiguity, no XCUITest target) per RESEARCH §Open Question 1.

The hand-rolled error view shape mirrors what the configuration would render:

- centered `UIImageView` with `UIImage(systemName: "wifi.exclamationmark")`
- heading `UILabel` (`font = DS.Typography.title2`, `textColor = DS.Colors.label`)
- body `UILabel` (`font = DS.Typography.body`, `textColor = DS.Colors.labelSecondary`)
  carrying the VM's `loads.error.generic` message
- "Try again" `UIButton` with
  `accessibilityIdentifier = "loads-list.error-state.retry"` (set at
  `layoutContent()` time, NOT post-render)

The host stack view carries
`accessibilityIdentifier = "loads-list.error-state"`. Identifier coverage on
the error state is deterministic — no post-render walks, no internal-hierarchy
dependency.

## Decision impact on Task 3

- `.error` state: hand-rolled `errorStateView: UIStackView` background view
  pinned to the safe area, `isHidden = true` until `.error` fires.
- `.empty` state: unchanged — uses `UIContentUnavailableConfiguration.empty()`
  (no button in the empty path, so no identifier walk needed; only the
  configuration's text + image fields are populated).
- `.loaded` / `.loading`: unaffected — neither uses
  `contentUnavailableConfiguration`.

## Risk left open

If a future SDK exposes `ButtonProperties.accessibilityIdentifier` (Apple
opens the surface in iOS 18+), the hand-rolled view becomes redundant. The
file-level comment in `LoadListViewController.swift` notes the post-v1.1
opportunity to revisit. No urgency — XCUITest deterministic targeting is more
important than the marginal LOC savings of the configuration path.
