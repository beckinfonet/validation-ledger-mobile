## Resolution

root_cause: "ROUND 3 (decisive on-device evidence). The KYC capture preview is solid black because `previewContainer` (the host view for the AVCaptureVideoPreviewLayer) collapses to ZERO height — confirmed: the device log shows `previewContainer.bounds={{0,0},{0,0}}` at viewDidLayoutSubviews. The proximate cause is the ROUND-2 fix itself (commit 873becd): the rigid 3:4 aspect-ratio constraint (`previewContainer.heightAnchor == widthAnchor * 4/3`, layout name `kyc-face-preview`) is UNSATISFIABLE. The host `UIStackView` is pinned to the safe area on BOTH the top (+32) and the bottom (−32), so the stack's height is fully determined; its other arranged subviews (instruction + cue labels, and the vehicle shutter button) have intrinsic heights, leaving a fixed amount of vertical slack. The 4:3 aspect ratio demands more height than that slack, so the layout is over-constrained — UIKit resolves it by FORCE-BREAKING the aspect constraint (`Will attempt to recover by breaking constraint kyc-face-preview.height == 1.33333*kyc-face-preview.width`). With the aspect constraint broken, `previewContainer` — a plain UIView with no intrinsic content size and no other height constraint — is under-determined again and collapses to height 0. `previewLayer.frame = previewContainer.bounds` then copies a 0×0 rect → the AVCaptureVideoPreviewLayer renders nothing → only the container's `.black` background shows. Round 2 swapped 'zero because no constraint' for 'zero because the constraint gets force-broken' — identical net effect. The camera session is healthy and is NOT the cause: the device log shows authorization resolved (.authorized), front camera discovered, 1 input + 1 output committed, and `isRunning=true`. The permission/session wiring from b2983a9 is correct and is kept."
fix: "Removed the rigid 3:4 aspect-ratio constraint (the force-broken constraint — the round-3 root cause) from both FaceCaptureViewController and VehicleCaptureViewController. `videoGravity = .resizeAspectFill` already makes the preview layer fill whatever frame the container gets, so a fixed aspect ratio is unnecessary for correct video. Replaced it with the mechanism a `.fill` UIStackView is designed to use: the preview container's vertical content-hugging AND compression-resistance priorities are set to 1 (the lowest possible) while the instruction + cue labels hug vertically at `.required` (and the vehicle shutter button keeps its `>= 44` floor) — so the `.fill` stack is FORCED to expand the preview into all leftover vertical space. The stack height is positive and fully pinned; the labels take only their intrinsic height; the remainder handed to the preview is therefore always > 0, and there is no conflicting constraint left for UIKit to break. Defense-in-depth: a `previewContainer.heightAnchor >= 240` floor at priority 250 — too low to fight the `UIView-Encapsulated-Layout-Height` (so it can never reintroduce a breakable conflict) yet it guards against any future layout change shrinking the preview. `stack.distribution = .fill` is now set explicitly. The `kyc_camera` instrumentation from rounds 1–2 is kept for one more on-device confirmation. b2983a9 (permission gating + off-main session calls) is untouched."
