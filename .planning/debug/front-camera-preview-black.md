## Resolution

root_cause: "ROUND 3 (decisive on-device evidence). The KYC capture preview is solid black because `previewContainer` (the host view for the AVCaptureVideoPreviewLayer) collapses to ZERO height — confirmed: the device log shows `previewContainer.bounds={{0,0},{0,0}}` at viewDidLayoutSubviews. The proximate cause is the ROUND-2 fix itself (commit 873becd): the rigid 3:4 aspect-ratio constraint (`previewContainer.heightAnchor == widthAnchor * 4/3`, layout name `kyc-face-preview`) is UNSATISFIABLE. The host `UIStackView` is pinned to the safe area on BOTH the top (+32) and the bottom (−32), so the stack's height is fully determined; its other arranged subviews (instruction + cue labels, and the vehicle shutter button) have intrinsic heights, leaving a fixed amount of vertical slack. The 4:3 aspect ratio demands more height than that slack, so the layout is over-constrained — UIKit resolves it by FORCE-BREAKING the aspect constraint (`Will attempt to recover by breaking constraint kyc-face-preview.height == 1.33333*kyc-face-preview.width`). With the aspect constraint broken, `previewContainer` — a plain UIView with no intrinsic content size and no other height constraint — is under-determined again and collapses to height 0. `previewLayer.frame = previewContainer.bounds` then copies a 0×0 rect → the AVCaptureVideoPreviewLayer renders nothing → only the container's `.black` background shows. Round 2 swapped 'zero because no constraint' for 'zero because the constraint gets force-broken' — identical net effect. The camera session is healthy and is NOT the cause: the device log shows authorization resolved (.authorized), front camera discovered, 1 input + 1 output committed, and `isRunning=true`. The permission/session wiring from b2983a9 is correct and is kept."
fix: "ROUND 4 (structural). Two layers of fix this round: (1) STRUCTURAL PREVIEW HOST — replaced the fragile manual pattern (add an `AVCaptureVideoPreviewLayer` as a sublayer of a plain `UIView`, then re-sync `previewLayer.frame = previewContainer.bounds` on every `viewDidLayoutSubviews`) with the idiomatic `layerClass` pattern. NEW file `CameraPreviewView.swift`: a `UIView` subclass with `override class var layerClass: AnyClass { AVCaptureVideoPreviewLayer.self }` — its BACKING layer IS the preview layer, which UIKit keeps EXACTLY `bounds`-sized at all times with zero manual work. There is no `.frame` to sync and no window where the layer is sized differently from the view — the 0×0 manual-sync race is permanently impossible. `FaceCaptureViewController` + `VehicleCaptureViewController` (and via subclass `DLBackCaptureViewController`) now host the preview in a `CameraPreviewView`; the session is wired into `previewView.session`; the oval guide is a sibling sublayer of the preview view's layer. The round-3 hugging-priority `.fill`-stack layout is RETAINED (it correctly resolved the constraint conflict). (2) DEFINITIVE DIAGNOSTIC — a one-shot `kyc_camera event=final_state` log, scheduled ~2s after `startAuthorizedSession` is kicked (on the main actor), emits ONE post-settle line capturing `view.bounds`, `view.window`, `navController`, `previewView.bounds`, `previewLayer.bounds`, `previewLayer.superlayer`, `sessionWired`, `sessionRunning`, and the connection's exists/active/enabled — removing the round-3 ambiguity of whether the tester's console capture caught the final layout pass. `FigCaptureSourceRemote err=-17281` needs NO fix — WebSearch (Apple Developer Forums 808736/810894/808479) confirms it is benign internal AVFoundation log noise; frames are still delivered. The coordinator path was audited and is sound (`.kyc` phase installs the KYC nav directly as `window.rootViewController`; the face VC is a full-screen pushed VC). b2983a9 (permission gating) + 93386af (the round-3 layout fix) are both kept untouched."
