## Critical Gaps (block a clean close)

### 1. Phase 4 was never verified — no `04-VERIFICATION.md`

Phases 1, 2, 3, 5 each have a `VERIFICATION.md` (all `human_needed`, all 5/5
success criteria). **Phase 4 has only `04-VALIDATION.md` — no verification
report exists.** Phase 4 (App Attest + device CI) was never run through
`/gsd-verify-work`. Per the audit rule, an unverified phase is a blocker — and
in this case it directly hid gap #2 below.

### 2. DEV-04 — App Attest is not invoked at first OTP login

DEV-04 and Phase 4 SC-1 require App Attest on the **first successful OTP
verify**, with the assertion carried in `/device/register`. The code does not
do this:

- `OTPViewModel.swift:202-211` hardcodes `attestationStatus: .unsupported`,
  `attestedKeyId: nil`, `attestationObject: nil` and never calls
  `container.attestationService`.
- The in-code comment (lines 189-193) states *"Plan 06 AppContainer wiring will
  replace this with an AttestationService call"* — **that replacement never
  landed**, yet `04-06-SUMMARY.md` claims DEV-04.
- App Attest runs only later, via `SceneDelegate.performHeartbeatIfNeeded()` on
  cold-boot restore / 24h warm-foreground — never in the first-login session.
- The `/device/register` response is discarded (`_ = try await ...`), so
  `AppSession.trustTier` is never set from the login path and defaults to
  `.softwareOnly` until the next cold-boot heartbeat.

The attestation *infrastructure* is real and works (Core/Attestation,
`AttestationService`, `AttestedKeyStore`, heartbeat path, `/device/register`
three-key payload). What is missing is the first-login trigger and the response
consumer. This is **partial**, not absent — but the literal DEV-04 promise
("on first successful login") is unmet.

Phase 4's own `deferred-items.md` documents the `trustTier` consumer half as a
**user-accepted follow-up (2026-04-22)**. The attestation-at-first-login half is
documented only in the stale OTPViewModel code comment.

## Integration Findings (cross-phase wiring)

Spawned `gsd-integration-checker`; 6 of 8 E2E flows wired end-to-end. The two
broken seams:

- **BLOCKER (DEV-04):** OTP-verify → `/device/register` → `AppSession.trustTier`
  — response discarded at `OTPViewModel.swift:202`. (Same root cause as gap #2.)
- **Low severity (KYC-05):** Profile → KYC status screen "Continue" CTA is a
  dead button. `AppContainer.makeKYCStatusScreen()` (line 178-185) builds the
  view model without wiring `onVerified`; `KYCCoordinator.pushStatus()`
  (line 497) — the post-submit path — does wire it. Impact is cosmetic: the
  Profile entry is only reachable from inside the role shell (already verified),
  so "Continue" is redundant navigation. Worth a one-line fix, not a blocker.

Two warnings (correctness, not blocking):

- **WARNING-1 (SESS-01 / KYC-01 / D-13):** Keychain `kycStatus` is written only
  at OTP-verify, never refreshed after a successful `GET /kyc/status`. A user
  who OTP-verifies with a non-verified status, completes KYC **in-session**,
  then force-quits is routed back into the KYC gate on cold boot (the fail-closed
  probe sees a stale/absent `kycStatus`). Happy-path fixtures mask this.
- **WARNING-2 (DEV-04 / D-11):** `LimitedTrustBannerView` is rendered once at
  role-shell construction; the heartbeat mutates `trustTier` but cannot
  re-render/remove the banner until the next root-swap.

The `AppContainer` composition root is otherwise sound — all Phase 2-5 services
are constructed and consumed (`SensitiveActionService` has zero M1 call sites,
which is intentional per AUTH-06).
