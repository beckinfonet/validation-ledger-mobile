# Phase 10 — UI Design Contract

> Visual and interaction contract for the **Per-Role Tender / Accept / Reject** phase — the screen where the v1.1 platform thesis ("identity that cannot be spoofed") becomes a tap. Generated by gsd-ui-researcher, verified downstream by gsd-ui-checker.
>
> **Platform note:** Native iOS UIKit client (iPhone + iPad, iOS 17+). The shadcn initialization gate and component-registry safety gate are **not applicable** — no `components.json`, no Tailwind, no React. The "Design System" section describes the existing in-repo UIKit token layer (`validationLedger/UI/DesignSystem/`).
>
> **Phase 10 frame** (orchestrator-supplied): Make loads actionable on the detail screen. 9 requirements (ACTION-01..09). The action region is mounted INSIDE `LoadDetailBodyView`'s vertical scroll stack between the status timeline and the freight detail rows (CONTEXT D-01). Optimistic UI predicts the load forward on tap; the chain-of-trust card is **never** predicted (D-13 — predicting trust contradicts the platform thesis). Failure rolls back the load + slides in a top toast banner with **localized fixed copy** (server text never reaches the screen — extends Phase 9 D-20 / T-09-04 view-layer lock). ACTION-07 enforces "no tender to an unverified counterparty" at two surfaces: the load-level Tender button (`Load.tenderEligibility.canTender`) and the carrier row inside the new tender sheet (verification state on each carrier).

## UIKit vs SwiftUI Decision (locked — inherited from Phases 9 / 9.1)

**Decision: UIKit, programmatic, no XIB / Storyboard.**

The action surface is critical-class UI: a misfire on the Tender button (e.g. accidentally letting the broker tender to an unverified counterparty because a SwiftUI binding cycle missed the disabled flag) is a fraud vector. CLAUDE.md reserves UIKit for exactly this class. Every Phase 9 / 9.1 rationale carries forward. Concretely:

- **View controllers:** `LoadDetailViewController` is MODIFIED (renders 2 new VM states — `.actionInFlight`, `.actionFailed`; mounts the action region inside the body; presents the toast banner; presents the tender sheet). One NEW view controller: `TenderSheetViewController` (the modal sheet content VC). All programmatic constructors; `required init?(coder:)` traps. ARCH-04.
- **New views (all `UIView` subclasses):** `LoadActionsView` (`Features/Loads/Detail/`), `LoadActionToastBannerView` (`Features/Loads/Detail/` or `UI/Components/` — planner discretion), the chain "updating…" overlay subview (likely inline on the VC; planner discretion). All programmatic.
- **Modal sheets:** `UISheetPresentationController` with `.medium` detent (`.large` available for tall accessibility content sizes), iOS 17+ native. ONE source of presentation infrastructure across `VerificationBasisSheetViewController` (Phase 9), `HandoffDetailSheetViewController` (Phase 9), and the new `TenderSheetViewController` (Phase 10).
- **No pull-to-refresh on the detail screen.** Phase 9 contract preserved.
- **No new third-party dependency.** The toast banner is a hand-rolled `UIView` with `UIView.animate` + `transform` + `alpha`. No SnackBar library, no Toast-Swift import.

## Screen Composition Touch Points (extends Phase 9 / 9.1)

Phase 10 modifies the existing iPhone + iPad compositions established in Phase 9 and 9.1. The action region is inserted; nothing is removed; the chain card region gains a transient overlay during in-flight; the VC gains a transient top-anchored toast banner.

### iPhone (`horizontalSizeClass == .compact`) — modified composition

```
┌─────────────────────────────────────┐
│ [TOAST BANNER — transient]          │  ← TOP, slides down on .actionFailed
├─────────────────────────────────────┤
│ ◂ Back            Loads             │  ← Nav bar (system)
├─────────────────────────────────────┤
│ Pinned summary header               │
├─────────────────────────────────────┤
│ EveryoneOnLoadStripView   [overlay] │  ← 9.1 strip — "updating…" overlay during .actionInFlight
├─────────────────────────────────────┤
│                                     │
│   ChainOfVouchesView      [overlay] │  ← 9.1 card — same overlay
│                                     │
├═════════════════════════════════════┤  ← Scroll boundary
│ Status timeline                     │  ← (Phase 9 — re-renders against predicted Load during in-flight)
├─────────────────────────────────────┤
│ ┌─ LoadActionsView ─────────────┐   │  ← NEW (Phase 10) — inserts between timeline + freight
│ │ [ Tender ] [ Accept ]         │   │     side-by-side equal-width buttons (D-02)
│ │ ↳ "Not verified — cannot…"    │   │     inline disabled-reason (ACTION-07 load-level gate)
│ └───────────────────────────────┘   │
├─────────────────────────────────────┤
│ Freight detail rows                 │
├─────────────────────────────────────┤
│ Parties (inline list)               │
├─────────────────────────────────────┤
│ Chain-integrity verdict block       │
└─────────────────────────────────────┘
```

- **Action region position:** between `StatusTimelineView` and the freight detail rows in `LoadDetailBodyView.contentStack`. Mounts as the 3rd `arrangedSubview` (after `pinnedSummaryHeader` at index 0 and `timelineContainer` at index 1). Inserts at `index 2`; the existing freight/parties/verdict subviews shift down by one. No top-level composition rebuild needed (CONTEXT D-01 — the body owns the scroll order).
- **Toast banner position:** transient subview of the VC's root view, pinned to `safeAreaLayoutGuide.topAnchor`, leading/trailing pinned to `view.layoutMarginsGuide` with `DS.Spacing.md` (16pt) horizontal inset. Z-order: ABOVE the nav bar's visual area (the banner sits over the nav-bar baseline by ~8pt) so it never gets visually clipped by the nav. NOT a child of the body scroll view — it must remain pinned during scroll.
- **Chain "updating…" overlay:** a single transient subview pinned over the iPhone chain region (the strip + card combined bounding rect). Bounded by `EveryoneOnLoadStripView.topAnchor → ChainOfVouchesView.bottomAnchor` (the 9.1 components' frames define the overlay's geometry). NOT a child of either chain component — pinned by the VC so it can be added/removed without touching 9.1 internals.

## Spacing Scale

INHERITED from `DS.Spacing` (Phase 1). Phase 10 declares which existing token each new surface binds to. **No new spacing tokens.**

| Token | Value | Phase 10 usage |
|-------|-------|----------------|
| `xs`  | 4pt  | Disabled-reason inline label → button vertical gap; spinner → label inline gap inside in-flight button |
| `sm`  | 8pt  | Inter-button spacing in the equal-weight horizontal row; deadline chip-to-chip inline spacing; toast icon → label inline spacing |
| `md`  | 16pt | Action region content insets (leading/trailing match the freight rows above/below); tender sheet content margins; toast banner content insets; deadline section vertical gap |
| `lg`  | 24pt | Action region top + bottom vertical padding inside `LoadDetailBodyView.contentStack`; tender sheet section vertical gap (carrier list ↔ deadline picker ↔ Send button); toast banner bottom-of-screen margin from `safeAreaLayoutGuide.topAnchor` (negative — i.e. banner pulls down 24pt past safe area to "land" visibly under the nav) |
| `xl`  | 32pt | (NOT used in Phase 10 — reserved for chain-block separation per 9.1 R8) |
| `xxl` | 48pt | (NOT used in Phase 10) |

**Exceptions:**

- **44pt minimum touch target** on every interactive surface — action buttons, carrier rows in the tender picker, deadline preset chips, the Custom… row, the Send / Cancel buttons in the sheet, the toast-banner swipe-to-dismiss surface, the disabled-state surfaces (still 44pt hit area even when `isEnabled = false`, so a user tapping a disabled control gets an accessibility focus / VoiceOver hit and reads the disabled reason).
- **Action button minimum height: 50pt** (greater than 44pt floor). Rationale: at the standard Dynamic Type setting the title baseline reads cleanly with `DS.Typography.headline`; smaller would visually compete with the freight-row label height and make the action region feel like "just another row." The 50pt height is enforced via `UIButton.Configuration.buttonSize = .medium` plus an explicit `heightAnchor.constraint(greaterThanOrEqualToConstant: 50)`.
- **Toast banner minimum height: 56pt** (greater than 44pt floor). Rationale: the icon + multi-line label may wrap at large Dynamic Type sizes; 56pt is the comfortable minimum for an iOS toast/banner per Apple HIG (see Notifications style).
- **Chain overlay opacity: 0.6 on a `DS.Colors.surface` backdrop** (NOT a spacing exception; documented here for proximity). The overlay is NOT a full opaque blocker — the chain remains partially visible underneath so the user always sees "the chain is what it was; it will refresh." A subtle activity indicator (`UIActivityIndicatorView` `.medium` style, tinted `.label`, centered in the overlay) signals "updating."

## Typography

INHERITED from `DS.Typography`. Phase 10 declares which existing token each surface binds to. **No new typography tokens.**

| Role | Token | Resolves to | Weight | Phase 10 usage |
|------|-------|-------------|--------|----------------|
| Body      | `DS.Typography.body`     | `.body`     | regular  | Carrier name in the tender picker; deadline chip resolved-time line; toast banner body label |
| Heading   | `DS.Typography.headline` | `.headline` | semibold | Action button title ("Tender", "Accept", "Reject", "Advance to in-transit", …); tender sheet "Send" button title; tender sheet section headers ("Carrier", "Respond by"); toast banner inline title (if used in 2-line form) |
| Label     | `DS.Typography.footnote` | `.footnote` | regular  | Disabled-reason inline copy below the Tender button (ACTION-07 load-level); verification reason copy under each disabled carrier row in the picker; tender sheet helper line under the Send button; respond-by static rendering on the carrier/dispatch view of `.tendered` |
| Caption   | `DS.Typography.caption`  | `.caption1` | regular  | Empty-state caption text ("This is a view-only role. No actions available.", "This load is delivered. No actions available."); the in-flight spinner's optional inline caption ("Submitting…") if displayed alongside the spinner |

**Weight discipline (2 weights only — UI-SPEC universal rule):**

- **Regular** (`.regular`) — body, label, caption, disabled reason, helper text.
- **Semibold** (`.semibold`) — action button titles, Send button title, sheet section headers, toast banner inline title.

No other weight is permitted. Dynamic Type scales both weights identically. The action button title's semibold weight is the Phase-10 declaration that "this is the primary action surface of the screen" — without bolder vs. regular hierarchy WITHIN the row (D-02 — both buttons in a fork are equal weight semantically; both render semibold).

**Line heights:** all labels use `UILabel`'s default line-height for the bound text style. Multi-line surfaces:

- Disabled-reason inline label: `numberOfLines = 2`, `lineBreakMode = .byWordWrapping`. Allows "Tender unavailable — counterparty's USDOT authority is suspended" to wrap to a second line at smaller widths.
- Toast banner body label: `numberOfLines = 2`, `lineBreakMode = .byWordWrapping`. Same rationale — the 1-line "Couldn't send tender. Try again." remains 1 line at standard widths but can wrap at larger Dynamic Type.
- Carrier name in picker: `numberOfLines = 1`, `lineBreakMode = .byTruncatingTail`. Long carrier names truncate; the full name lives in `accessibilityLabel`.

## Color

Built on `DS.Colors`. The 60/30/10 rule applies to non-fraud-signal surfaces — the destructive red (Reject / Cancel button tint, action-failure toast tint when the action was destructive) deliberately escapes the 10% rule because the entire premise of the action region is that destructive outcomes MUST be visually distinct from constructive ones.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%)  | `DS.Colors.background` (`.systemBackground`)         | `LoadDetailBodyView` scroll background (already established); tender sheet's outer background. |
| Secondary (30%) | `DS.Colors.surface` (`.secondarySystemBackground`)  | Action region's internal background (visually distinct from the page background, so the action region reads as a discrete block within the body); tender sheet's grouped-row carrier-list background; deadline preset chip unselected fill; chain "updating…" overlay backdrop (@ 0.6 alpha). |
| Accent (10%)    | `DS.Colors.primary` (`.systemBlue`)                 | **Reserved-for list (explicit):** (1) constructive action button background (Tender, Accept, Advance, Post) via `UIButton.Configuration.filled().baseBackgroundColor`; (2) selected deadline chip fill; (3) selected carrier row's checkmark accessory icon; (4) tender sheet's "Send" button background. The selected chip and selected carrier are the two interaction-state surfaces the broker confirms before sending. |
| Destructive     | `DS.Colors.destructive` (`.systemRed`)              | **Reserved-for list (explicit):** (1) destructive action button background (Reject, Cancel) via `UIButton.Configuration.filled().baseBackgroundColor`; (2) toast banner background when the failed action was destructive (Reject, Cancel); (3) flagged-carrier `VerificationBadgeView` background in the tender picker (delegated through `DS.Colors.Verification.color(for: .flagged)` — 9.1 lock). |

**Accent reserved for:** the four items above. NEVER used for: tender sheet chrome (uses `surface`); empty-state caption background (no background — just text); the in-flight button's spinner tint (the spinner inherits the button's title color so it reads as `.white` against either blue or red — Apple HIG default).

**Destructive tint reserved for:** the three items above. The Cancel button in the tender sheet (which dismisses the sheet WITHOUT submitting an action) is NOT a destructive button — it uses `UIButton.Configuration.borderless()` with `baseForegroundColor = DS.Colors.primary`. "Cancel the sheet" is a navigation, not a destructive action against the load.

**Action button color → action mapping (LOCKED):**

| `LoadAction` case | Button tint | Configuration |
|-------------------|-------------|---------------|
| `.tender`        | `DS.Colors.primary` (blue) | `.filled()` |
| `.accept`        | `DS.Colors.primary` (blue) | `.filled()` |
| `.advanceStatus` | `DS.Colors.primary` (blue) | `.filled()` |
| `.post`          | `DS.Colors.primary` (blue) | `.filled()` |
| `.reject`        | `DS.Colors.destructive` (red) | `.filled()` |
| `.cancel`        | `DS.Colors.destructive` (red) | `.filled()` |

D-02 / D-03: both buttons in a fork are equal weight in LAYOUT (equal `.fillEqually` width); they differ in TINT (destructive vs. constructive) so the visual signal of "this one undoes / unwinds the load" is clear without forcing a primary-vs-secondary hierarchy.

**Disabled state (every button — constructive AND destructive):**

- `isEnabled = false` → `UIButton.Configuration` uses the system disabled treatment (lighter tint, reduced opacity to ~0.4). NO custom disabled-color override.
- The disabled button's `accessibilityHint` is set to the human-readable reason (e.g. "Disabled: counterparty unverified") so VoiceOver users hear why immediately.
- The disabled-reason INLINE LABEL beneath the button (only used for the load-level ACTION-07 gate on Tender) renders in `DS.Colors.labelSecondary` with `DS.Typography.footnote`. Single 0.5pt `DS.Colors.separator` between button and inline label? NO — too noisy. Just `DS.Spacing.xs` (4pt) vertical gap.

**In-flight state (active button after tap, before server response — `.actionInFlight`):**

- The TAPPED button: `isEnabled = false`, `UIActivityIndicatorView` `.medium` style centered over the title, title alpha → 0. The button retains its tint (NOT switched to grey) — the user reads "the action I just initiated is still my action; it's just in flight." 250ms ease-in fade for the title-out / spinner-in.
- ALL OTHER buttons in the action region: `isEnabled = false`, standard system disabled treatment (lighter, ~0.4 opacity). Prevents double-submit and prevents the user from initiating a competing action mid-flight.
- The chain "updating…" overlay fades in over the chain region: `alpha 0 → 0.6` over 200ms.

**Toast banner color → action mapping (LOCKED):**

| Failed action | Banner background | Foreground (icon + label) |
|---------------|-------------------|---------------------------|
| `.tender` / `.accept` / `.advanceStatus` / `.post` | `DS.Colors.destructive.withAlphaComponent(0.92)` | `.white` |
| `.reject` / `.cancel`                              | `DS.Colors.destructive.withAlphaComponent(0.92)` | `.white` |

All failure toasts use the same red tint — a failure on a constructive action is still a failure; the banner is a failure signal, not a constructive-vs-destructive signal. The red @ 0.92 (not full 1.0) gives the banner a hair of translucency so the underlying status bar / nav bar reads through subtly — visually identifies the banner as a transient layer, not a permanent surface.

**Important — destructive vs. error palette DISTINCTION:**

- **Destructive button tint** (Reject, Cancel) uses `DS.Colors.destructive`. This signals "this action will undo / unwind".
- **Failure toast** also uses `DS.Colors.destructive`. This signals "this action failed."
- Both are red — same token, two distinct contexts. The toast is presented at the TOP of the screen, transient (3–4s), and slides in; the button is in the body, persistent, and rendered statically. The two surfaces never co-render in the same place; ambiguity is impossible. (This is consistent with Phase 9's overlap of `.systemRed` for `.flagged` badges + `.compromised` chain banner + Phase 5 destructive-confirm — one red, multiple security contexts.)

## Copywriting Contract

All user-facing strings are `NSLocalizedString`-wrapped with a phase-prefixed key (`loads.actions.*` or `loads.detail.tender.*`) and a descriptive `comment` argument. M1 ships English-only; v2 i18n readiness is the precedent.

### Action button titles (LOCKED — one per `LoadAction` case)

| `LoadAction` case | Button title | NSLocalizedString key |
|-------------------|--------------|----------------------|
| `.tender`        | `Tender`     | `loads.actions.button.tender` |
| `.accept`        | `Accept`     | `loads.actions.button.accept` |
| `.reject`        | `Reject`     | `loads.actions.button.reject` |
| `.cancel`        | `Cancel load` | `loads.actions.button.cancel` |
| `.post`          | `Post`       | `loads.actions.button.post` |
| `.advanceStatus` | (dynamic — see below) | `loads.actions.button.advance.<targetStatus>` |

**`.advanceStatus` title resolution:** the button title is computed from the load's NEXT canonical state (which the carrier/dispatch infers by reading the current `LoadStatus`):

| Current `LoadStatus` | Next status | Button title | Key |
|----------------------|-------------|--------------|-----|
| `.accepted`     | `.dispatched`  | `Dispatch`             | `loads.actions.button.advance.dispatched` |
| `.dispatched`   | `.inTransit`   | `Mark in transit`      | `loads.actions.button.advance.in_transit` |
| `.inTransit`    | `.delivered`   | `Mark delivered`       | `loads.actions.button.advance.delivered` |

The next-state lookup is a small helper on the action-bar (planner: pure function `nextStatus(from: LoadStatus) -> LoadStatus?`); it is NOT a `switch load.status` in a view controller (ROADMAP § Phase 10 lock — but resolving a BUTTON TITLE from `LoadStatus` is different from GATING actions on `LoadStatus`; the gate stays with `RoleLoadPolicy`). The button is only RENDERED when `RoleLoadPolicy.actions(for:status:).contains(.advanceStatus)`; the next-state resolver only fires once the gate is open.

### ACTION-07 disabled-reason inline copy (LOCKED)

Below the disabled Tender button — single line by default, wraps to 2 lines at large Dynamic Type sizes. Two sources:

| Condition | Source | Fallback |
|-----------|--------|----------|
| `Load.tenderEligibility?.canTender == false` AND `Load.tenderEligibility?.disabledReason != nil` AND non-empty | Server-supplied `disabledReason` rendered verbatim (e.g. "Counterparty USDOT authority suspended") | — |
| `Load.tenderEligibility?.canTender == false` AND `disabledReason == nil` (or empty) | `loads.actions.tender.disabled.generic` → `Tender unavailable` | (no further fallback) |

**Important — `Load.tenderEligibility.disabledReason` is server-supplied and rendered:** this is a DOCUMENTED exception to the "no server text on the screen" rule (which CONTEXT D-15 / Phase 9 D-20 / T-09-04 apply to ERROR text from action failure responses). `disabledReason` is part of the STATIC load shape (loaded with the load detail itself, not as an error response payload); it carries the verified-counterparty thesis explicitly to the user. The negative-text lock applies to ACTION FAILURE response bodies, not to load-state metadata. The two surfaces are read at different times by the user and cannot mix.

The inline label uses `DS.Typography.footnote`, `DS.Colors.labelSecondary`, `numberOfLines = 2`, `lineBreakMode = .byWordWrapping`. Left-aligned, leading-anchored to the leading edge of the Tender button's leading edge (NOT centered) — the eye scans from the button to the reason without re-aligning.

### Empty-state captions (LOCKED — `RoleLoadPolicy.actions(...) == []`)

The action region stays present in the body's scroll stack (CONTEXT D-04 — never collapses to zero height; never hides). Renders a single centered caption row in place of buttons:

| Condition | Caption | NSLocalizedString key |

### Respond-by countdown copy (carrier / dispatch view of `.tendered`)

Decision (UI-SPEC discretion per CONTEXT § Deferred): **Static rendering**, not a live-updating countdown timer.

Rationale: a live `Timer`-driven counter introduces a re-render cadence and a "the deadline just passed" edge case (CONTEXT § Deferred captured this as a post-v1.1 follow-up). The static form is informative, accessible (VoiceOver reads it once with a calm cadence; a live counter would announce every minute), and matches the freight industry's familiar "respond by 5 PM" cadence. The data source (`Load.respondByAt: Date`) is locked; v1.1 ships static; a live variant is a one-paragraph follow-up if product asks.

| Element | Copy | Key |
|---------|------|-----|

| Past-deadline visual variant (when `Load.respondByAt < now` AND load is still `.tendered`) | `Past due — respond by %@` | `loads.actions.respond_by.past_due.format` |

**Date format:** `DateFormatter` with `.relative` style + `.short` time fallback:

- Today: `"5:00 PM today"`
- Tomorrow: `"5:00 PM tomorrow"`
- 2–6 days out: `"5:00 PM, Wed"` (weekday short)
- 7+ days out: `"5:00 PM, May 28"` (medium date)

Decision (UI-SPEC discretion per CONTEXT D-15 + § Claude's Discretion): **One toast per `LoadAction` case** (per-action taxonomy), NOT a single generic copy with action-name interpolation. Rationale: separate keys give the localization team room to phrase each failure naturally in target languages (e.g. "Couldn't send tender" in English vs. a passive construction in Spanish); a single-key interpolation forces every language into the same grammatical shape. The 6 strings are not a maintenance burden.

### Predicted-state behavior

When the user taps an action button, the VM transitions to `.actionInFlight`. The detail VC re-renders against the predicted `Load` value. Specifically:

| UI element | Behavior during `.actionInFlight` |
|------------|-----------------------------------|
| Pinned summary header — `LoadStatusBadgeView` | Renders the PREDICTED status (e.g. on tender: `.posted → .tendered`). |
| Status timeline (`StatusTimelineView`) | Re-renders against the predicted `Load.stateHistory + Load.status`. The current-state pill advances. |
| Action region (`LoadActionsView`) | Re-renders against `RoleLoadPolicy.actions(for: role, status: predictedStatus)`. The available action set advances (e.g. on tender: from `[.tender, .cancel]` to `[]` since the broker's post-tender action set on `.tendered` is empty per the policy — actually, planner re-verifies against `RoleLoadPolicy` table; the indicative example is illustrative). The TAPPED button shows its spinner; all other buttons are disabled. |
| EveryoneOnLoadStripView + ChainOfVouchesView (iPhone) / TrustGraphView (iPad) | **UNCHANGED.** Render the pre-tap `ChainOfTrust`. The chain "updating…" overlay fades in over the region. |
| Freight detail rows, Parties inline list, Chain-integrity verdict block | UNCHANGED. (None of these surfaces is affected by an action in v1.1.) |
| Toast banner | Not present yet — only appears on `.actionFailed`. |

On 200 success: the predicted state is REPLACED by `response.load + response.chainOfTrust`; the chain overlay fades out; the action region re-renders against the fresh state.

On error: the predicted state is rolled back to the pre-tap `Load` value; the chain overlay fades out (the chain wasn't predicted, so there's nothing to roll back there); the toast banner slides in.

| Carrier / Dispatch | `.dispatched` | `[.advanceStatus]`         | 1 button: blue "Mark in transit" |
| Carrier / Dispatch | `.inTransit`  | `[.advanceStatus]`         | 1 button: blue "Mark delivered" |
| Carrier / Dispatch | `.delivered`  | `[]`                       | Terminal-state caption |
| Carrier / Dispatch | all other states | `[]`                    | Empty caption (the carrier doesn't act on `.draft`, `.posted`, `.rejected`, `.expired`, `.cancelled`, post-delivery) |

**Tender-eligibility-gate overlay on the table:** for Shipper/Broker rows where `[.tender, ...] ∈ available actions`, the Tender button respects `Load.tenderEligibility?.canTender == false` and renders disabled with the inline reason. The Cancel button is NEVER gated by `tenderEligibility` — cancellation is always available when the policy says so.

**Planner verification gate:** Phase 10 plan must include a test that snapshot-renders the action region for EVERY `(Role × LoadStatus)` combination — 5 × 13 = 65 snapshots. (Many are visually identical empty-state captions; the snapshot suite is the gate that the action-region UI matches `RoleLoadPolicy` exhaustively.)

**VoiceOver focus order** (iPhone, in-flight state during a Tender):
1. Pinned summary header (predicted status badge speaks "Tendered")
2. EveryoneOnLoadStripView — strip chips (chain is frozen; speaks pre-tap state — the overlay's "chain refreshing" announces separately via `accessibilityViewIsModal = false` + `accessibilityElements`)
3. ChainOfVouchesView — tree rows (frozen)
4. Chain overlay's "Chain refreshing" announcement (read once on focus, then `.updatesFrequently` polls less aggressively per Apple HIG)
5. StatusTimelineView — current state pill speaks "Tendered, current"
6. LoadActionsView — tapped button speaks "Tender, submitting" + spinner is `.updatesFrequently`
7. Other action buttons (if any) speak "[title], unavailable while submitting"
8. Freight detail rows, Parties list, Verdict block

**VoiceOver toast announcement:** when the banner slides in, the VC posts `UIAccessibility.post(notification: .announcement, argument: <toast text>)`. This is the iOS-native pattern for transient notifications (matches Apple's own "Mail sent" / "Note saved" toasts).

**Dynamic Type:** every label uses Dynamic Type-aware `UIFont.preferredFont(forTextStyle:)`. At `.accessibilityLarge` and above, the action button row flips to `.vertical` axis (see Component Geometry above) so titles never truncate. The tender sheet's `.medium` detent automatically grows to `.large` if content overflows.

**Color contrast (WCAG AA):**
- White text on `DS.Colors.primary` (`.systemBlue`) — passes AA at all sizes (system semantic, dark-mode-adaptive).
- White text on `DS.Colors.destructive` (`.systemRed`) — passes AA at all sizes.
- `DS.Colors.labelSecondary` on `DS.Colors.surface` — passes AA per iOS system semantics (the system semantic pair is designed to meet WCAG).
- Toast: white text on `DS.Colors.destructive @ 0.92` over the underlying nav bar/background — passes AA (red @ 0.92 has effective luminance close enough to red @ 1.0 to remain compliant).
