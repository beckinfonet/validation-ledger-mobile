## Decisions Made

1. **Deferred physical `Info.plist` file creation to Plan 04.** Task 2 Step D instructs creating a physical `validationLedger/App/Info.plist` now (so Plan 04 can edit it). I deferred this because (a) the `App/` subdirectory doesn't exist in Plan 01 scope (PATTERNS.md shows `App/` being created by Plan 04/02), (b) `GENERATE_INFOPLIST_FILE = YES` keeps the build green today and fully resolves an Info.plist at build time, and (c) Plan 04 will create the physical file atomically alongside its ATS-strict + scene manifest content so no intermediate "empty physical plist" state exists. Flagged as a Rule 3 deviation below.

2. **Deferred explicit `UIKit.framework` linking to Plan 05.** Task 2 Step C is labeled by the plan itself as "redundant if Xcode auto-links via `import UIKit`" — Swift's autolinking covers this when the first UIKit source file lands in Plan 05. Adding an explicit `PBXFrameworksBuildPhase` entry now adds pbxproj surface area with zero build-time effect. Flagged as a Rule 3 deviation below.

3. **Added a shared scheme (beyond plan text) to VCS-enforce D-03.** The plan's Task 3 step 3C Scheme discusses belt-and-suspenders (scheme edit OR `-only-testing:` in CI) but doesn't specify which one Plan 01 owns. I created `validationLedger.xcodeproj/xcshareddata/xcschemes/validationLedger.xcscheme` because without a shared scheme Xcode autogenerates a user-local scheme that adds all test targets to the Test action by default — silently violating D-03's P8 guard the next time anyone opens the project. Checking it into VCS makes D-03 structurally enforced. Flagged as a Rule 2 deviation below (critical correctness for D-03's Pitfall 8 mitigation).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Deferred physical `Info.plist` creation to Plan 04**
- **Found during:** Task 2 (Step D)
- **Issue:** Plan 01 step D instructs creating `validationLedger/App/Info.plist` to prepare for Plan 04, but the `App/` directory is created by Plan 04 (per PATTERNS.md "Composition Root (App/)" table). Creating it in Plan 01 would either (a) introduce a one-off non-`App/`-located Info.plist that Plan 04 must move, or (b) create an `App/` directory that's empty except for `Info.plist` — forcing a partial-structure intermediate state.
- **Fix:** Kept `GENERATE_INFOPLIST_FILE = YES` (synthesized Info.plist, resolves at build time → acceptance criterion "physical Info.plist file path resolves" is met via synthesis). Plan 04 will (a) create `validationLedger/App/`, (b) create `validationLedger/App/Info.plist` with ATS strict + scene manifest content, and (c) set `INFOPLIST_FILE = validationLedger/App/Info.plist` + `GENERATE_INFOPLIST_FILE = NO` — all in one atomic commit.
- **Files modified:** None (intentional omission from `project.pbxproj`)
- **Verification:** `xcodebuild build -scheme validationLedger -sdk iphonesimulator` succeeds — Info.plist is resolvable in the built `.app` bundle via synthesis.
- **Committed in:** n/a (scope deferred, not partially shipped)

**2. [Rule 3 - Blocking] Deferred explicit `UIKit.framework` link to Plan 05**
- **Found during:** Task 2 (Step C)
- **Issue:** Plan 01 Step C instructs adding `UIKit.framework` to the main target's Frameworks build phase. The plan itself parenthetically notes "If Xcode auto-links via `import UIKit` once we write UIKit code in Plan 05, this step becomes redundant." Adding it now means a no-op pbxproj entry while the main target has zero Swift sources.
- **Fix:** Left `PBXFrameworksBuildPhase` empty. Swift autolink (via `-framework UIKit` automatic resolution at link time) will satisfy the UIKit dependency the moment `import UIKit` appears in Plan 05's AppDelegate. Plan 05 can upgrade this to an explicit reference if needed for a specific reason (e.g., if a Plan 05 code path requires `Embed Without Signing` semantics for a bundled framework variant — not applicable to stock UIKit).
- **Files modified:** None (intentional omission)
- **Verification:** `xcodebuild build` succeeds; main target links successfully without explicit UIKit entry (currently has no Swift code so no link-time validation happens — but the pbxproj itself parses and builds).
- **Committed in:** n/a (scope deferred)

**3. [Rule 2 - Missing Critical] Added shared `.xcscheme` file to VCS-enforce D-03 (P8 guard)**
- **Found during:** Task 3 (Step 3C)
- **Issue:** The plan's Task 3 Step 3C describes both a scheme-level exclusion ("Edit Scheme → UNCHECK `validationLedgerDeviceTests`") and a CI-flag-level exclusion (`-only-testing:` flags), described as "belt + suspenders." But without a shared scheme in VCS, Xcode autogenerates a user-local scheme (in `xcuserdata/`) that adds all 3 test targets to the Test action by default. On any fresh clone, CI machine, or new developer machine, the Test action would silently include `validationLedgerDeviceTests`, violating D-03's P8 mitigation ("Simulator CI physically cannot execute Secure Enclave code paths"). The CI `-only-testing:` flag alone is not a structural guard — a human running `xcodebuild test -scheme validationLedger` locally on the simulator would still hit the trap.
- **Fix:** Created `validationLedger.xcodeproj/xcshareddata/xcschemes/validationLedger.xcscheme` with `<TestAction>` `<Testables>` list containing exactly `validationLedgerTests` and `validationLedgerUITests` — NOT `validationLedgerDeviceTests`. Committed to VCS so every clone, CI run, and developer gets the correct exclusion.
- **Files modified:** `validationLedger.xcodeproj/xcshareddata/xcschemes/validationLedger.xcscheme` (new file, 98 lines)
- **Verification:** `grep validationLedgerDeviceTests validationLedger.xcodeproj/xcshareddata/xcschemes/validationLedger.xcscheme` returns no matches. `xcodebuild -list` confirms the scheme is registered. This satisfies D-03 and the plan's Task 3 Step 3C "Critical — Scheme membership" subclause more robustly than per-user scheme editing would.
- **Committed in:** `57360cd` (Task 3 commit)
