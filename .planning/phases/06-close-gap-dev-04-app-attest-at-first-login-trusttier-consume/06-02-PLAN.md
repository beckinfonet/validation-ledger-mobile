The heartbeat path is the orchestration TEMPLATE — read SceneDelegate.performHeartbeatIfNeeded
(SceneDelegate.swift:568-651) before writing STEP 5. The first-login path is the same shape with
two endpoints swapped (delta table below).

AttestationService (validationLedger/Core/Attestation/AttestationService.swift):
  - `generateKeyIfNeeded() async throws -> (keyId: String, status: AttestationStatus)`
    — idempotent, once-per-install (Phase 4 D-01).
  - `attestKey(keyId:challenge:) async throws -> Data` — returns the attestationObject.
  - Selected in AppContainer.init via `#if DEBUG && targetEnvironment(simulator)`
    (DCAppAttestAttestationService / SimulatorBypassAttestationService); OTPViewModel
    just consumes `container.attestationService`.

AttestationStatus — closed-set enum: `.attested`, `.simulatorBypass`, `.unsupported`,
  `.entitlementMissing`, `.quotaExceeded`, `.error`. `.attested` and `.simulatorBypass` are the
  two "usable key" states; everything else is graceful-skip (D6-04).

DeviceChallengeEndpoint — `GET /device/challenge`; `Response { challenge: String (base64),
  expiresAt, nonce }`. base64-decode `challenge` to raw `Data` before use.

DeviceRegisterEndpoint — `POST /device/register`, already a 6-arg initializer:
  `DeviceRegisterEndpoint(devicePublicKey:, authorizationPublicKey:, attestedKeyId:,
  attestationObject:, attestationStatus:, fingerprint:)`. `attestedKeyId` and
  `attestationObject` are `Optional` — Swift's JSONEncoder drops `Optional.none` (no `null`
  on the wire), so passing `nil` IS the D-09 omission rule (Pattern B — do NOT hand-code
  field stripping). `Response { deviceID, registeredAt, trustTier: TrustTier }`.

AttestationErrorResponseInterceptor.extractErrorCode(from: Data?) -> String? — `internal static`
  (AttestationErrorResponseInterceptor.swift:132); tolerant JSON parse, accepts both `error_code`
  and `errorCode`, returns `nil` on malformed input. Reuse this for the D6-06 challengeExpired
  body parse — do NOT write a new JSON parser.

NetworkError.httpError(statusCode: Int, data: Data?) — the register POST surfaces a stale
  challenge as this case, carrying the response body.

OTPViewModel.init (OTPViewModel.swift:88-104) — current signature takes
  `(otpSessionID:, apiClient:, keychain:, keyStore:, biometric:, sessionLock:, logger:)`.
  AuthCoordinator.pushOTP (AuthCoordinator.swift:50-59) is the SINGLE construction site.

The .settingUp(progress:total:) state — keep `total: 6`; the attestation work folds into the
  existing `progress: 4` STEP 5 slot (06-RESEARCH Pitfall 4 / Assumption A3 — M1 minimal-UI).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → backend (`POST /device/register`, `GET /device/challenge`) | Untrusted-network requests cross here; the attestation payload and challenge transit the wire. |
| backend → client (register/challenge responses) | `trustTier`, `challenge`, and the `error_code` body are untrusted input decoded by typed endpoints. |
| App Attest service (Apple `DCAppAttestService`) → app | `attestKey` / `generateKeyIfNeeded` cross into Apple-managed crypto; errors may carry diagnostic `NSError.userInfo`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-02-01 | Information Disclosure | New attestation `catch`/log calls in `OTPViewModel.verify()` STEP 5 leaking `attestationObject` / challenge bytes / `NSError.userInfo` | mitigate | D6-07 / Pattern A — attestation catches log only the event name + `AttestationStatus.rawValue` (closed-set string); never `String(describing: error)`. Task 1 ships a source-grep test that fails the build if `String(describing:` appears in an attestation catch. |
| T-06-02-02 | Denial of Service | First-login attestation failure used to block a legitimate login (DoS-by-strictness) | mitigate | D6-05 — a transient attestation failure degrades to `attestationStatus: .error`, omits fields, and STILL POSTs `/device/register`; login always completes. App Attest is never a login gate (matches Phase 4 D-09 / SC-2). |
| T-06-02-03 | Tampering / Spoofing | A stale/replayed challenge accepted by `/device/register` | mitigate | D6-06 — a `challengeExpired` server error triggers a fresh `GET /device/challenge` + re-`attestKey` + a single register retry; the challenge is backend-issued and short-TTL. A second consecutive expiry surfaces rather than looping. |
| T-06-02-04 | Repudiation | Register POST replayed (e.g. on `retryRegister()`) creating duplicate device records | accept | `/device/register` is `Idempotency-Key`-protected (NET-04); the backend dedupes. `generateKeyIfNeeded` is once-per-install (Phase 4 D-01). `retryRegister()` re-running `verify()` is therefore safe — Task 1 pins this with a retry test. |
| T-06-02-05 | Tampering | Malformed `challengeExpired` error body crashing the parse | mitigate | The body parse reuses `AttestationErrorResponseInterceptor.extractErrorCode` — a tolerant `JSONSerialization` parse that returns `nil` on malformed input (no crash, fail-safe to no-retry). |
| T-06-02-SC | Tampering | npm/pip/cargo installs | mitigate | N/A — Phase 6 installs zero packages (06-RESEARCH Package Legitimacy Audit: not applicable). App Attest uses Apple's `DeviceCheck`, already on the CLAUDE.md pre-approved shortlist. |
</threat_model>
