## Shared verification color helper location

| Option | Description | Selected |
|--------|-------------|----------|
| Inside `DS.Colors` as a nested `Verification` type | Add a `Verification` namespace inside `DS.Colors` (in `Colors.swift`). Both views call `DS.Colors.Verification.color(for: state)`. Keeps everything design-system colocated — the Phase 9 `DS.Colors.caution` token already lives there. Smallest footprint, one file touched. | ✓ |
| New file `VerificationColorRamp.swift` | Sibling file under `UI/DesignSystem/`. Public enum with a `static func color(for: VerificationState) -> UIColor`. More findable when grepping; clearer that the ramp is a distinct concept. One new file. | |
| Extension on `VerificationState` | `var badgeColor: UIColor` extension in a new `VerificationState+Color.swift` under `UI/DesignSystem/`. Reads as `state.badgeColor`. Most idiomatic Swift, but couples the enum to UIKit in a sibling file. | |

**User's choice:** Inside `DS.Colors` as a nested type.
**Notes:** The Phase 9 `DS.Colors.caution` token already lives in `Colors.swift`, so the nesting keeps the "all design-system tokens in one file" rule intact. The shared helper exposes only the background color (which is also the dot color on the new `RoleAvatarView`); the `VerificationBadgeView` keeps owning its icon, label copy, label text color, and `accessibilityLabel` inline because those aren't shared with the avatar.

## Strip-tap interactivity (backlog open question)

| Option | Description | Selected |
|--------|-------------|----------|
| Static — strip is decoration, no tap behavior | Chips are non-interactive. Each chip is its own a11y leaf with composed role-name + display-name + verification-state label. Smallest 9.1 surface; the reference's "selected chip" treatment is deferred. | |
| Tap-to-scroll — chip tap scrolls the tree and gives the row a brief highlight | Chip becomes a button-trait a11y leaf; tap recognizer scrolls `ChainOfVouchesView` to put the matching row at the top + applies a green outline like the reference. Adds gesture tests + a brief animation, matches the reference photo most directly. | ✓ |
| Tap selects but no scroll/animation — visual selection only | Chip tap toggles selected visual on chip AND matching tree row, no scrolling or animation. Lighter than the scroll variant but heavier than static. | |

**User's choice:** Tap-to-scroll — chip tap scrolls the tree to that role's row and gives it a brief highlight.
**Notes:** Selection state is keyed by `Role`, not `partyID`, because the strip collapses multi-broker chains into one chip per SPEC R2. The exact highlight visual (color token, outline thickness, animation duration, fade behavior) is UI-SPEC 9.1 territory.

## Multi-broker strip-tap semantics (VL-1009)

| Option | Description | Selected |
|--------|-------------|----------|
| Both broker rows highlight; tree scrolls so both are visible | Both FreightWise and Keystone rows get the outline; scroll target is the top of the broker sibling group so both are on-screen. Matches "the role is suspect, not just one party" — the chameleon-broker fraud signaling intent. | ✓ |
| First broker row highlights; tree scrolls to it | Only the first broker in canonical chain order gets the outline. Simpler selection model (single selected partyID, not a set). Less aligned with the dual-broker fraud-signaling intent. | |
| Cycle through brokers on repeated taps | First tap highlights broker 1; second tap on the same chip highlights broker 2; third cycles back. Most discoverable for power users but adds state to track and isn't in the reference photo. | |

**User's choice:** Both broker rows highlight; tree scrolls so both are visible.
**Notes:** Forces the tree's selection API to be `applySelectedRole(_ role: Role?)` rather than `applySelectedParty(_ partyID: String?)`. Aligns with the platform thesis: the chameleon-broker pattern in VL-1009 is a role-level fraud signal, not a per-party one.

The user accepted that gap reading and chose to proceed to CONTEXT + UI-spec without locking the 🟡 copy in CONTEXT.

## DEBUG-only iPhone 2D-graph fallback toggle (backlog open question)

| Option | Description | Selected |
|--------|-------------|----------|
| No — pure replacement, iPad-only graph | iPhone only ever renders the new strip + tree. Marketing shots come from the iPad simulator. Cleanest; less surface area to maintain; no dead branch in production binary. | |
| Yes — add `-Mock2DTrustGraphOnIPhone`, DEBUG-only | Mirrors `-MockKYCStatusVerified` precedent. iPhone layout picks 2D vs. vertical tree based on the launch arg. Cost: ~1 if-branch + ~1 unit test + a comment block. Preserves the visually striking marquee for App Store screenshots. | ✓ |
| Defer to a separate phase if/when marketing needs it | Don't add the toggle now; capture as deferred. Zero added complexity in 9.1; some future toil if it does turn out to be wanted. | |

**User's choice:** Yes — add `-Mock2DTrustGraphOnIPhone`, DEBUG-only.
**Notes:** Mirrors the `-MockKYCStatusVerified` precedent (`MockDefaultFixtures.swift` lines 32, 69, 71). Strictly `#if DEBUG`-gated; the flag and the branch are stripped from Release builds. Intended use is App Store screenshots and press shots — the pulse-on-compromised animation reads as marketing-quality even though the chips are unreadable at iPhone widths.
