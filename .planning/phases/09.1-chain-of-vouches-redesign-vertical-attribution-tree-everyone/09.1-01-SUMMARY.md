## Decisions Made

- **Single-shared `backgroundColor` assignment hoisted above the switch.** The plan said "HOIST a single `backgroundColor = DS.Colors.Verification.color(for: state)` assignment OUTSIDE the switch (place it as the first line of the function body, before the switch)." The implementation places it as the first executable line of `apply(state:)`, with a 5-line rationale comment block above it that re-points readers at the TRUST-02 invariant home in `Colors.swift`. The result: the switch body now ONLY owns per-case differences (SF Symbol, tint, label text, label color, accessibilityLabel) — exactly the D-02 contract.
- **TRUST-02 lock comment placement: relocate primary, brief cross-reference at old home.** D-02 allowed either "relocated OR duplicated." Chose RELOCATE (primary block lives at the helper declaration) + a short 8-line cross-reference appended to the `VerificationBadgeView.swift` header pointing at the new home. Rationale: duplicating the entire block invites drift; a short cross-reference keeps both surfaces searchable without two copies of the same prose.
- **Test class declared `final class`.** The Patterns map noted "both shapes exist — `class` (per the snapshot test) vs. `final class` (per Phase 9 trust-graph tests); planner chooses." Chose `final class` because there is no subclass requirement on this test and `final` matches the more recent Phase 9 precedent.
- **No `setUp`/`tearDown` overrides.** The 4 tests construct fresh `VerificationBadgeView` instances inline (matches the snapshot test's pattern). No shared state — each test is independent.
- **`-only-testing` argument shape:** the plan said `-only-testing:validationLedgerTests/VerificationBadgeViewTests` (no `/Components` segment despite the file living in `Components/`). The xcodebuild syntax `validationLedgerTests/<ClassName>` uses the CLASS name, not the path — confirmed working on the new file.

## Issues Encountered

- **R12 strict-gate grep has a known false positive.** The plan's Task 3 strict-gate command iterates over every file containing `case .verified:` / `case .pending:` / etc., and flags it if a brand-color literal appears within 3 lines. `validationLedger/Features/Onboarding/KYC/KYCStatusViewController.swift` matches — but its switch is on `KYCStatusViewModel.State`, NOT `VerificationState`. The case names coincidentally overlap (`verified`, `pending`); `DS.Colors.primary` is used at lines 254-255 as the icon tint + text color for the KYC "you're verified" screen, NOT as a VerificationState → UIColor mapping. **The substantive R12 invariant is intact** — the primary gate (consumer-set match) passes exactly, and a tightened strict gate excluding this pre-existing file confirms no real violation. This is a pre-existing condition (not introduced by this plan) and is a known limitation of the grep-based strict gate (cannot distinguish enum types statically). Resolution paths if it ever bites: (a) refine the strict gate to require the switch line + 3 lines and ensure the enum type, (b) annotate `KYCStatusViewController.swift` with a `// not VerificationState — KYCStatusViewModel.State` marker the gate could allow-list, (c) accept the heuristic and document as here. No change in this plan.
