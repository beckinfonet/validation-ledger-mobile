# Phase 4 Plan 4: Device Endpoints — Wire Contract Summary

Wire-format contract for Phase 4 attestation flow: two new endpoints (DeviceChallenge GET, DeviceHeartbeat POST) + non-breaking extension of DeviceRegisterEndpoint with the three-key payload (D-02), attestationStatus (D-09), and trustTier response (D-12). Plan 03's DCAppAttestAttestationService and Plan 06's AppContainer wiring now have the types they need to compile.

## Deliverables

### DeviceChallengeEndpoint (new, GET)

- Path: `/device/challenge`, method: GET, RequestBody: `EmptyBody`.
- Response: `{ challenge: String, expiresAt: Date, nonce: String }`.
- Decodes `device-challenge-success.json` fixture (Wave 1) — `expires_at` → `expiresAt` via `.convertFromSnakeCase`, ISO-8601 dates via `.iso8601`.
- `nonisolated public struct` for main-actor-isolation compliance (Phase 2 pattern).
- D-05 challenge contract + D-08 single-use immediate-consumption — client never caches.

### DeviceHeartbeatEndpoint (new, POST)

- Path: `/device/heartbeat`, method: POST.
- RequestBody: `{ sessionToken: String, attestedKeyId: String, assertion: Data }` — `Data` wire-serializes as base64 by default.
- Response: `{ heartbeatAcceptedAt: Date, trustTier: TrustTier }`.
- Decodes `device-heartbeat-success.json` fixture (Wave 1); error path fixture `device-heartbeat-attestation-invalid.json` is consumed by Plan 05's error-interceptor test.
- IdempotencyInterceptor (NET-04) injects a per-heartbeat UUID Idempotency-Key (04-RESEARCH Pattern 3).

### DeviceRegisterEndpoint (extended in-place)

- RequestBody now carries **6 fields** (3 existing + 3 new + 1 reshaped):
  - `devicePublicKey: String` — existing (Phase 2 DEV-01)
  - `authorizationPublicKey: String` — **NEW on the wire** (Phase 4 DEV-02, D-02)
  - `attestedKeyId: String?` — NEW (D-09, omitted when not .attested)
  - `attestationObject: Data?` — NEW (D-09, omitted when not .attested)
  - `attestationStatus: AttestationStatus` — NEW required (D-09 six-value enum)
  - `deviceFingerprint: DeviceFingerprintPayload` — existing (Phase 2 DEV-05)
- Response adds `trustTier: TrustTier` (D-12) alongside existing `deviceID` + `registeredAt`.
- CodingKeys preserve `deviceID` → `deviceId` acronym bridge and snake-case bridge `trust_tier` → `trustTier`.
- Single Phase 4 `init` — Phase 2's 2-arg init was replaced (not supplemented).

### D-09 Omission Rule

Swift's `JSONEncoder` with default strategy silently omits `Optional.none` properties — no `"null"` in the JSON payload. When `attestationStatus != .attested`, callers pass `attestedKeyId: nil` and `attestationObject: nil`, producing a payload that contains neither key. Plan 05 adds a parametrized test (`DeviceRegisterOmissionTests.omittedWhenNotAttested`) that explicitly pins this behavior against the five non-`.attested` AttestationStatus cases.

## Deviations from Plan

### Rule 3 — Auto-fix Blocking Issue: Caller migration of old 2-arg `DeviceRegisterEndpoint` init

**Trigger:** Plan expected `grep "DeviceRegisterEndpoint(devicePublicKey:" = 0` in Phase 2/3 production code. Actual grep turned up THREE callers of the old 2-arg signature:
- `validationLedger/Features/Onboarding/Auth/OTPViewModel.swift:169` (production — Phase 3 Plan 09)
- `validationLedgerTests/Networking/APIClientEndpointTests.swift:162, 191` (Phase 2 tests)

Plan text said "If any non-Plan-06 caller exists, raise a blocker." But Plan 06 only touches AppSession.swift + AppContainer.swift — it does NOT migrate OTPViewModel. Leaving the old init in as a back-compat shim would have violated the plan's pinned acceptance criterion (`grep "public init(" = 1`). Removing the old init without migrating the callers would have broken the Wave 2 build, blocking the parallel Plan 05 executor.

**Fix (applied in Task 2 commit):**
1. OTPViewModel now reads `keys.authorizationPublicKey` (previously discarded) and passes `authorizationPublicKey: authPub.base64EncodedString()` + `attestationStatus: .unsupported` + nil attestation fields. This is a latent Phase 2 bug fix: the authorization key was being generated in Secure Enclave but never put on the wire — now it is. When Plan 06 AppContainer wiring lands, OTPViewModel will call an `AttestationService` to supply the real status + optional attestation fields.
2. Two test callers in APIClientEndpointTests updated to use the 6-arg init with placeholder auth key and `.unsupported` status.

**Verification:** All 14 APIClientEndpointTests pass; `xcodebuild build` succeeds with 0 errors.

**Note on one acceptance-criterion imprecision:** Plan said `grep "public init(" = 1`. Actual count is 2 because `DeviceFingerprintPayload.init(model:iosVersion:installUUID:)` is a nested Phase 2 struct init that was already present. The endpoint's own top-level init count is 1 — matching the plan's intent ("single Phase 4 init"). Non-functional imprecision in the grep counter.

### Rule 3 — Auto-fix Blocking Issue: device-register-success.json fixture missing trust_tier

**Trigger:** Phase 4 makes `DeviceRegisterEndpoint.Response.trustTier: TrustTier` non-optional (required). The Phase 2 happy-path fixture `device-register-success.json` did not include a `trust_tier` field, so the existing `deviceRegisterSuccess` test would fail with a decoding error.

**Fix:** Added `"trust_tier": "hardwareAttested"` to the fixture. Additive change — preserves existing `device_id` + `registered_at` and matches the Wave 1 shape used by `device-register-software-only.json`.
