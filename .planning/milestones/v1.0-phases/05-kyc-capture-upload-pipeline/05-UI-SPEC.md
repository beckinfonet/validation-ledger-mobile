# Phase 5 — UI Design Contract

> Visual and interaction contract for the KYC Capture & Upload Pipeline phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Platform note:** This is a native iOS UIKit client (iPhone + iPad, iOS 17+), not a web project. The shadcn initialization gate and component-registry gate are **not applicable** — there is no `components.json`, no Tailwind, no React. The "Design System" below describes the existing in-repo UIKit token layer (`validationLedger/UI/DesignSystem/`) plus the Apple frameworks used for capture surfaces. All KYC/camera/scanner screens are UIKit `UIViewController`s per the CLAUDE.md sensitive-surface mandate (SwiftUI is forbidden on camera layers).

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (native UIKit — no shadcn / no web design system) |
| Preset | not applicable |
| Component library | UIKit + `UIButton.Configuration` system styles; capture surfaces use `AVFoundation` (camera) + `Vision` (face quality gates) + `VisionKit.DataScannerViewController` (DL OCR) |
| Icon library | SF Symbols (system; via `UIImage(systemName:)`) — no third-party icon set |
| Font | San Francisco (system font via `UIFont.preferredFont(forTextStyle:)` — Dynamic Type enabled, `adjustsFontForContentSizeCategory = true`) |

**In-repo token namespace:** `DS` enum (`validationLedger/UI/DesignSystem/`) — `DS.Spacing`, `DS.Typography`, `DS.Colors`. Phase 5 screens MUST consume these tokens, not raw literals. The existing Auth screens (`PhoneEntryViewController`, `OTPViewController`) currently use raw `8 / 12 / 16 / 24 / 32` literals — Phase 5 must use the `DS.Spacing` tokens instead (the literals map cleanly: 8 → `sm`, 16 → `md`, 24 → `lg`, 32 → `xl`). The 12pt value used in the OTP stack spacing is **not** on the 4pt grid as a named token; Phase 5 uses `sm` (8) or `md` (16) instead — see Spacing Exceptions.

## Spacing Scale

Declared values — the existing `DS.Spacing` enum (`validationLedger/UI/DesignSystem/Spacing.swift`), all multiples of 4:

| Token | `DS.Spacing` member | Value | Usage in Phase 5 |
|-------|---------------------|-------|------------------|
| xs | `DS.Spacing.xs` | 4px | Icon-to-label gaps, thumbnail status-badge inset |
| sm | `DS.Spacing.sm` | 8px | Compact vertical spacing inside a review thumbnail cell; chip padding |
| md | `DS.Spacing.md` | 16px | Default `UIStackView` spacing; default screen content padding |
| lg | `DS.Spacing.lg` | 24px | Screen leading/trailing safe-area inset (matches Auth screens); section gap on the status screen |
| xl | `DS.Spacing.xl` | 32px | Top inset from `safeAreaLayoutGuide.topAnchor` (matches Auth screens); spacing above primary CTA |
| xxl | `DS.Spacing.xxl` | 48px | Major break between the framing-guide area and the capture controls; empty-state vertical centering offset |

**Exceptions:**
- **44pt minimum touch target** — the shutter button, "Use photo"/"Retake" buttons, per-artifact "Retry upload"/"Retake" controls on the Review screen, and the pull-to-refresh affordance must each present a hit area ≥ 44×44pt (Apple HIG minimum). 44 is not a `DS.Spacing` token; it is an explicit touch-target floor.
- **Camera framing-guide geometry** (oval face guide stroke width, DL rectangle inset) is driven by the capture preview-layer bounds and Vision/`DataScanner` region-of-interest math, not the 4pt grid. The guide *outer margins* still pin to `DS.Spacing` (`lg` = 24 from screen edges).
- The legacy `12pt` stack spacing seen in `OTPViewController` is **not** adopted — Phase 5 uses `DS.Spacing.sm` (8) for compact stacks and `DS.Spacing.md` (16) for default stacks. No new sub-16 token is introduced.

## Typography

Phase 5 uses the existing `DS.Typography` tokens (`validationLedger/UI/DesignSystem/Typography.swift`), all backed by `UIFont.preferredFont(forTextStyle:)` so Dynamic Type and dark mode are automatic. iOS text styles already encode size + weight + leading per the system; the table below pins the **four roles Phase 5 declares** and the system metrics at the default (Large) content size for the executor's reference. Every label MUST set `adjustsFontForContentSizeCategory = true`.

| Role | `DS.Typography` token | Text style | Size (default) | Weight | Line height (default) | Used for |
|------|----------------------|------------|----------------|--------|------------------------|----------|
| Display | `DS.Typography.title1` | `.title1` | 28pt | regular (400) | ~34pt (≈1.21) | Capture-screen instruction header ("Position your face"), KYC status verdict heading |
| Heading | `DS.Typography.headline` | `.headline` | 17pt | semibold (600) | ~22pt (≈1.29) | Section titles, "Review your photos", per-artifact labels on the Review/status list |
| Body | `DS.Typography.body` | `.body` | 17pt | regular (400) | ~22pt (≈1.29) | Primary CTA labels, extraction-confirmation field values, rejection-reason sentence copy |
| Caption | `DS.Typography.footnote` | `.footnote` | 13pt | regular (400) | ~18pt (≈1.38) | Inline status/error/progress text, GPS-staleness notices, upload progress percentage, the "Hold still" capture cue |

**Weights:** exactly two — **regular (400)** for body/display/caption and **semibold (600)** for headings. This is what the iOS `.headline` vs `.body`/`.title1`/`.footnote` styles already give for free; do not apply manual `.withWeight(...)` overrides. No bold, no light, no medium.

**Sizes:** exactly four roles declared (28 / 17 / 17 / 13). Body and Heading share the 17pt point size but differ by weight (regular vs semibold) — this is the standard iOS pairing and counts as the two distinct *roles* the contract requires. Do not introduce `.largeTitle`, `.title2`, `.callout`, or `.caption` from the token file for Phase 5 screens.

## Color

Phase 5 uses the existing `DS.Colors` tokens (`validationLedger/UI/DesignSystem/Colors.swift`), all mapped to iOS system semantic colors so dark mode and contrast are automatic. The 60/30/10 split below describes the KYC screens specifically.

| Role | Token / system color | Usage |
|------|----------------------|-------|
| Dominant (60%) | `DS.Colors.background` (`.systemBackground`) | Full-screen background of all non-camera KYC screens (review, status, extraction-confirmation, permission-denied). On camera screens the live `AVCaptureVideoPreviewLayer` is the dominant surface. |
| Secondary (30%) | `DS.Colors.surface` (`.secondarySystemBackground`) | Review-screen artifact thumbnail cells, the status-screen per-artifact rows, the extraction-confirmation field container. Camera-overlay scrim (semi-transparent dark) framing the oval/rectangle guide. |
| Accent (10%) | `DS.Colors.primary` (`.systemBlue`) | Reserved exclusively for the elements listed below. |
| Destructive | `.systemRed` (no token yet — Phase 5 adds `DS.Colors.destructive = .systemRed`) | Failed-upload status badge/text, rejection-reason text on the status screen, the inline OTP-style error label, the sign-out/cancel confirmation's destructive action. |

**Accent (`systemBlue`) reserved for:**
1. The primary CTA button on each screen (`UIButton.Configuration.borderedProminent()` — its tint is `systemBlue`): "Use photo", "Looks good", "Submit", "Continue".
2. The determinate `UIProgressView` progress fill during upload (`progressTintColor`).
3. The "✓ uploaded" success badge/checkmark on Review thumbnails and the "Verified" state indicator on the status screen.
4. Interactive text links — "Retake", "Rescan", "Retry upload" (`UIButton.Configuration.plain()` or `.bordered()`, tinted `systemBlue`).
5. The pull-to-refresh spinner tint on the status screen.

Accent is **not** applied to body text, backgrounds, separators, framing guides, or non-interactive labels.

**Capture-state guide colors (camera overlay — semantic, not on the 10% accent budget):**
- Face/DL framing guide **not yet passing** quality gates: `.white` at reduced alpha (neutral).
- Face/DL framing guide **passing** all gates / locked: `.systemGreen` (signals "ready" — distinct from the blue CTA accent and the red error color; this is a semantic capture-feedback color, kept off the brand accent budget).
- These two guide states plus the existing `LimitedTrustBannerView` `.systemYellow` caution tone are the only non-blue/non-red colors permitted, and each is justified by a distinct semantic meaning (ready / caution).

**Status-state color mapping (KYC status screen, KYC-05 / D-10):**
| KYC state | Color treatment |
|-----------|-----------------|
| Pending | `.secondaryLabel` neutral text + system "clock" SF Symbol |
| Under Review | `.secondaryLabel` neutral text + system "hourglass" SF Symbol |
| Verified | `DS.Colors.primary` (`systemBlue`) checkmark + label |
| Rejected | `DS.Colors.destructive` (`systemRed`) label + the controlled-vocabulary rejection-reason sentence in red, with a per-artifact "Retake" affordance in `systemBlue` |

## Copywriting Contract

All strings are wrapped in `NSLocalizedString` with an English `value:` fallback (matches the `LimitedTrustBannerView` pattern — M1 ships English only, `Resources/en.lproj/Localizable.strings` is structured for v2). Rejection-reason copy (D-11) is mapped from a backend reason **code** to an iOS-owned sentence via a typed Swift enum; the planner defines the controlled-vocabulary enum and a graceful fallback for unknown codes.

| Element | Copy |
|---------|------|
| Primary CTA — per-shot preview (D-07) | **"Use photo"** (paired secondary action: **"Retake"**) |
| Primary CTA — DL extraction confirm (D-05) | **"Looks good"** (paired secondary action: **"Rescan"**) |
| Primary CTA — Review screen (D-03) | **"Submit"** (disabled until all 6 artifacts are acked; helper caption below it when disabled: *"Submit unlocks once all 6 photos finish uploading."*) |
| Primary CTA — KYC status screen (verified path) | **"Continue"** (routes into the role shell once `overallStatus == verified`) |
| Capture cue — face auto-fire (D-04) | **"Hold still"** (shown for ~0.5s steady-hold before auto-capture); pre-pass instruction header: *"Position your face inside the oval."* |
| Capture cue — DL front | Instruction header: *"Fit your license inside the frame."* |
| Capture cue — DL back / vehicle | Instruction headers: *"Photograph the back of your license."* / *"Take a photo of the truck."* / *"…the trailer."* / *"…the license plate."* |
| Empty state heading — KYC flow start | **"Let's verify your identity"** |
| Empty state body — KYC flow start | *"We'll take 6 quick photos: your face, both sides of your license, and your truck, trailer, and plate. It takes about 2 minutes."* (CTA below: **"Get started"**) |
| Empty state — status screen, no submission yet | Heading: **"No verification in progress"** — body: *"Finish your KYC photos to start verification."* (this state is rare given the D-12 hard gate; included for the role-shell re-entry path) |
| Error state — camera permission denied (reuse Phase 3 D-21 pattern) | Heading: *"Camera access needed"* — body: *"Validation Ledger needs your camera to photograph your ID and vehicle. Turn it on in Settings."* — action: **"Open Settings"** / **"Cancel"** |
| Error state — GPS stale / quality-gate fail at capture | *"We couldn't confirm your location. Move to an open area and try the photo again."* (inline `.footnote`, `.secondaryLabel`; capture stays blocked until a fresh `<30s / <100m` fix is available) |
| Error state — face quality gate not passing | Live inline cue, no alert: *"Center your face"* / *"Move into better light"* / *"Hold the phone steady"* (Vision drives which is shown) |
| Error state — DL extraction format-check fail (D-05) | *"That scan didn't come through clearly — let's try again."* (auto-prompts a rescan) |
| Error state — upload retries exhausted (UPL-03, per artifact) | Inline on the Review thumbnail / status row: *"Upload failed."* — paired actions: **"Retry upload"** and **"Retake"** |
| Error state — network unavailable during upload | Non-blocking inline notice: *"Waiting for a connection — your photos will keep uploading automatically."* (uploads are pipelined/background per D-01; the user is not blocked) |
| Destructive confirmation — sign out / cancel inside the KYC gate (D-14) | **Sign out:** title *"Sign out of Validation Ledger?"* — body *"Your photos are saved on this device and will resume next time you sign in."* — destructive action **"Sign out"** (`.destructive`, runs `LogoutService.logout(reason: .userInitiated)`) + **"Stay"** (`.cancel`). |
| Destructive confirmation — discard in-progress KYC (D-02 explicit-discard path) | **Discard verification?** — body *"This deletes the photos you've taken so far. You'll start over next time."* — destructive action **"Discard"** (`.destructive`) + **"Keep"** (`.cancel`). |

**Submit semantics note for the planner:** "Submit" is a thin finalizer (D-03) — by the time it is tapped all 6 artifacts are already committed on the backend via the pipelined per-artifact upload (D-01). The disabled-state helper caption must make the gating mechanism obvious so the user does not read a disabled Submit as a bug.

## Registry Safety

**Not applicable.** This is a native iOS UIKit project. There is no shadcn registry, no `components.json`, and no third-party UI component registry. Dependencies are SwiftPM-only and pre-approved (CLAUDE.md): Phase 5 adds **no new UI dependency** — capture uses Apple-first-party frameworks already permitted (`AVFoundation`, `Vision`, `VisionKit`, `CoreImage`/`ImageIO` for EXIF injection, `CoreLocation`). Image display reuses `Nuke` (already pinned). The registry vetting gate is therefore vacuously satisfied.
