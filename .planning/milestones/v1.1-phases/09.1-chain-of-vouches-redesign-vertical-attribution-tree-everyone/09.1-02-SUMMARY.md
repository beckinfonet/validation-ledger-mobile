## Decisions Made

- **Internal-access subview properties (not `private`).** `abbreviationLabel` and `statusDot` are declared `let` without an explicit access modifier (default `internal`) so the unit-test target — running under `@testable import validationLedger` — can introspect them directly (`view.statusDot.backgroundColor`, `view.abbreviationLabel.text`). This mirrors Plan 01's `VerificationBadgeViewTests` precedent of asserting on view state via `@testable` rather than carving out per-test seams. The cost is a small surface increase visible to in-module code; the alternative (publishing computed `var statusDotColor: UIColor?` accessors purely for tests) would clutter the public API for no functional gain.
- **`layer.masksToBounds = false` on the avatar.** The status-dot subview is positioned at bottom-right with a `(+2, +2)` outward inset (so the dot's center sits at the avatar's bottom-right edge); the dot also wears a 2pt stroke ring in `DS.Colors.background` for the "punched-out" effect. Both the dot's body and its stroke must NOT be clipped by the avatar circle — so `masksToBounds` stays false. The avatar's circular shape is achieved via `cornerRadius = bounds.width / 2` on the chrome layer; the dot subview is a sibling that protrudes deliberately. VerificationBadgeView sets `masksToBounds = true` because its pill is content-clipped (label + symbol live inside); the avatar is the inverse case (chrome around its own content, with a sibling-chrome dot extending beyond).
- **`Variant` enum embeds geometry constants as computed properties.** Instead of `init(role:state:diameter:dotDiameter:dotInset:)` with five required CGFloat parameters, the public nested `enum Variant` carries `diameter`/`dotDiameter`/`dotInset` as computed-property switches. Result: a single place to change diameters when UI-SPEC refines the palette; the call site is `RoleAvatarView(role:state:variant: .strip)` — semantic at the call site, no risk of passing the wrong diameter for the variant. Test sites can also reference `RoleAvatarView.Variant.strip.diameter` if a future test needs it (unused in Plan 02 but a stable affordance).
- **40 explicit test methods over a parameterized loop.** A `forEach` loop driving the 40 cells would be ~40 lines vs. the chosen ~240 lines, but would surface a single failing test name (`test_renderAllCells`) on any failure — opaque in CI. The chosen shape mirrors `VerificationBadgeViewSnapshotTests`'s per-state methods, so a failing cell is named precisely (e.g. `test_broker_flagged_strip_rendersExpected`) in the Xcode test navigator. The legibility win is worth the line cost; this is also Pattern 6 the future composition snapshot suites (Plans 03+04) can mirror.
- **Single canvas size (80×80pt) for both variants.** UI-SPEC § Snapshot Test Matrix → Avatar row pins 80×80pt. Rendering the .tree variant (32pt avatar) inside the same canvas as the .strip variant (40pt) gives the reviewer extra padding around the smaller variant — a visual signal in the test report that "this is the smaller variant," reducing cognitive load when comparing 40 attachments side-by-side. A per-variant canvas would be tighter but visually confusable across the matrix.
- **PII grep-gate self-defense in the file header.** The initial draft of `RoleAvatarView.swift`'s "PII discipline" comment block listed the forbidden patterns by their literal token names (`os_log`, `Logger.`, `print(`). The R12-style grep gate in the plan's verify block scans for those exact regex patterns — and matched the documentation comment, falsely flagging the file. Fix: paraphrased the comment to describe the discipline without quoting the literals ("standard iOS logging APIs and stdout emit functions"). The gate now correctly returns empty. This pattern generalizes — any file documenting a forbidden-tokens lock should describe the discipline without quoting the tokens, so the gate doesn't fire on its own documentation.
- **`adjustsFontForContentSizeCategory = false` on `abbreviationLabel`.** Explicit `false` rather than implicit default. The view's deliberate Dynamic-Type exception (literal 11pt semibold for the abbreviation) is enforced at the property level; if a future "every label must scale" lint rule scans for `adjustsFontForContentSizeCategory = true`, the explicit `false` is the deliberate exception, locked. UI-SPEC § Accessibility Contract documents the rationale; the property setting honors it.
