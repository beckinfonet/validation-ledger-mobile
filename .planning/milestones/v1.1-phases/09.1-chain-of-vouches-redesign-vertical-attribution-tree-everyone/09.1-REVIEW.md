# Phase 09.1: Code Review Report

**Reviewed:** 2026-05-20T00:00:00Z
**Depth:** standard
**Files Reviewed:** 27
**Status:** issues_found

## Summary

Phase 09.1 ships a structurally clean Chain-of-Vouches redesign. The R9 multi-broker forced-siblings rule, R12 single-source-of-truth color helper (`DS.Colors.Verification` + `DS.Colors.Roles`), R10 iPad preservation (TrustGraphView untouched in `buildIPadSplitLayout`), R7 D-15 supersedure (no row dim / dashed / pulse on iPhone), R6 leaf-element accessibility model, and R11 `Core/Load/` freeze are all correctly executed. The view-layer PII lock holds — no `os_log`/`Logger`/`print` in any of the four new/modified view files. The R12 grep-gate consumer set is intact: only `VerificationBadgeView.swift` and `RoleAvatarView.swift` call the verification color helper, and `ChainOfVouchesView`'s footer-pill switch is over `ChainIntegrity.Verdict` (not `VerificationState`), so it does not violate the negative-grep gate.

That said, the implementation drifts from the spec in one binding way (WR-01 — the implicated-row suffix promised by SPEC R6 is silently omitted), produces a UX glitch (WR-02 — duplicate haptic on every chip tap), has a real-device dark-mode contrast bug on the caution footer pill (WR-03 — `.label` text on `.systemYellow` is white-on-yellow), has a latent timing bug in the chip-tap scroll handler that can crash on a cold first tap (WR-04), and has two test/build-time mismatches that will surface noisily during the first re-record pass (WR-05, WR-06). Info-level items are stylistic and inconsistency findings.

## Warnings

### WR-01: SPEC R6 implicated-row a11y suffix silently dropped

**File:** `validationLedger/Features/Loads/Detail/ChainOfVouchesView.swift:86-90, 417-443`
**Issue:** SPEC R6 (`09.1-SPEC.md` line 52) is binding: *"Implicated rows append the implicated-suffix per UI-SPEC line 845."* `composeRowLabel(node:parentNode:stateCopy:)` only takes `(node, parentNode, stateCopy)` — it never receives the chain's `ChainIntegrity.implicatedNodeIDs` set, and the row builder in `buildRows(from:)` never threads it through. The file-header rationale ("UI-SPEC.md ends at line 407 and locks no implicated suffix; R7 forbids any row-level fraud signaling on iPhone") conflates two different layers: R7 forbids **visual** row-level fraud signaling (alpha, dashing, pulse), but the **accessibility label** is a separate channel that SPEC R6 explicitly requires to carry the implicated state for VoiceOver users. As shipped, a VoiceOver user listening to VL-1009's flagged Keystone-Broker row hears only "Broker Keystone Freight Group, vouched by Shipper Global Exports Co., flagged" — they get the per-node state but no signal that this party is in the chain's implicated set. Sighted users get the footer pill; VoiceOver users get strictly less information.
**Fix:** Thread `chain.integrity.implicatedNodeIDs` into `composeRowLabel` and append a locked NSLocalizedString suffix when `implicatedNodeIDs.contains(node.partyID)`:
```swift
private func composeRowLabel(node: TrustNode, parentNode: TrustNode?,
                             stateCopy: String, isImplicated: Bool) -> String {
    var label = /* existing root / non-root format */
    if isImplicated {
        label += NSLocalizedString(
            "loads.detail.chain.9_1.row.a11y_label.implicated_suffix",
            value: ", implicated in chain compromise",
            comment: "Phase 9.1 implicated-row VoiceOver suffix per SPEC R6.")
    }
    return label
}
```
If product/UI-SPEC truly want the suffix omitted, the divergence must be re-locked in the spec text and the file header rationale rewritten — not justified inline against an out-of-bounds UI-SPEC line reference.

### WR-02: Duplicate haptic feedback fires on every strip-chip tap

**File:** `validationLedger/Features/Loads/Detail/EveryoneOnLoadStripView.swift:504-511`, `validationLedger/Features/Loads/Detail/LoadDetailViewController.swift:1093-1094`
**Issue:** Two `UISelectionFeedbackGenerator().selectionChanged()` calls fire on every chip tap:
1. `ChipView.handleTap()` (line 508-509) fires the haptic, then invokes `onTap?(role)`.
2. The strip forwards via `self.onRoleTap?(tappedRole)` → `LoadDetailViewController.handleStripChipTap(role:)` (line 1094) fires the haptic again.
On a physical device the user feels a doubled click. The duplication is also wasteful (each `UISelectionFeedbackGenerator()` allocates a new generator instance) and inconsistent with the inline contract comment on the strip ("Tap fires `UISelectionFeedbackGenerator.selectionChanged()` + the chip's `onTap` closure"), which intends a single haptic.
**Fix:** Remove the haptic from one site. Since the chip owns the gesture recognizer and is the natural source of the tap event, keep the haptic in `ChipView.handleTap()` and delete the `UISelectionFeedbackGenerator().selectionChanged()` call from `LoadDetailViewController.handleStripChipTap(role:)`:
```swift
// REMOVE from handleStripChipTap:
// UISelectionFeedbackGenerator().selectionChanged()
```

### WR-03: Caution footer pill is white-on-yellow in dark mode (a11y contrast failure)

**File:** `validationLedger/Features/Loads/Detail/ChainOfVouchesView.swift:847-863`
**Issue:** The `.caution` verdict branch in `ChainOfVouchesFooterPillView.apply(verdict:reason:)` sets `pillLabel.textColor = .label` on a `DS.Colors.caution` (= `.systemYellow`) background. `.label` is system-managed: black in light mode, **white in dark mode**. White-on-yellow fails WCAG AA contrast badly (~1.3:1 contrast ratio). All snapshot tests force `overrideUserInterfaceStyle = .light`, so the dark-mode regression is invisible in CI. On a real iPhone in dark mode (the freight dock at night is a documented use case in PROJECT.md), the caution-tier footer pill text becomes illegible — and the caution tier is precisely the "needs attention" signal users must read.
**Fix:** Either pin the label to a fixed dark color on the caution tier (matches `ChainIntegrityBannerView`'s existing caution-tier treatment), or use a dynamic color that adapts. Quickest fix that matches the LimitedTrustBannerView precedent:
```swift
case .caution:
    backgroundColor = DS.Colors.caution
    let cautionFG = UIColor { trait in
        trait.userInterfaceStyle == .dark ? .black : .label
    }
    pillLabel.textColor = cautionFG
    symbolView.tintColor = cautionFG
    // ...rest unchanged
```
Add a dark-mode snapshot variant (`overrideUserInterfaceStyle = .dark`) for the caution fixture to catch any future regression.

### WR-04: `handleStripChipTap` recurses via `DispatchQueue.main.async` with no bound on re-entry

**File:** `validationLedger/Features/Loads/Detail/LoadDetailViewController.swift:1061-1067`
**Issue:** The window-guard fallback defers the scroll to the next runloop tick:
```swift
guard iPhoneVerticalTreeScrollView.window != nil, allRowsInWindow else {
    DispatchQueue.main.async { [weak self] in
        self?.handleStripChipTap(role: role)
    }
    return
}
```
If the scroll view never enters a window (e.g., the user navigates away mid-flight, or this VC is configured then never presented because the parent flow changes course), `handleStripChipTap` re-enqueues itself on every runloop tick **forever** as long as `self` is alive — a permanent main-queue spinner that ties up the runloop. The `[weak self]` only breaks the loop after the VC is deallocated, which may take seconds during a transition animation. Worse: every iteration re-applies `chainOfVouchesView.applySelectedRole(role)` and `everyoneOnLoadStripView.applySelectedRole(role)`, both of which trigger CABasicAnimation work on the chip layers — wasted CPU.
**Fix:** Bound the retry count, or check that the chain has been configured before retrying:
```swift
private func handleStripChipTap(role: Role, retryCount: Int = 0) {
    // ... existing visual feedback ...
    let rows = chainOfVouchesView.rowViews(for: role)
    guard !rows.isEmpty else { return }
    let allRowsInWindow = rows.allSatisfy { $0.window != nil }
    guard iPhoneVerticalTreeScrollView.window != nil, allRowsInWindow else {
        guard retryCount < 3 else { return }  // bound the deferred retry
        DispatchQueue.main.async { [weak self] in
            self?.handleStripChipTap(role: role, retryCount: retryCount + 1)
        }
        return
    }
    // ... rest unchanged ...
}
```

### WR-05: Snapshot test method names lie about the device (iPhone 15 vs simulator iPhone 17)

**File:** `validationLedgerTests/Loads/Snapshot/ChainOfVouchesViewSnapshotTests.swift:58-61, 99-225`, `validationLedgerTests/Loads/Snapshot/EveryoneOnLoadStripViewSnapshotTests.swift:52-58, 98-192`
**Issue:** Test method names + attachment name templates encode `iPhone15Portrait` / `iPhoneSE3Portrait` at hardcoded canvas widths (390pt / 375pt). The SPEC explicitly says (`09.1-SPEC.md` line 131): *"All snapshot, unit, and UI tests pass on the scoped serial simulator lane (iPhone 17 + iPad regular size class)."* iPhone 17 portrait is 393pt — the canvas width disagrees with the device being targeted. The project-memory `ios-test-suite-pitfalls` already warns that the scoped lane uses a specific simulator; the snapshot-canvas naming now lies in a way that will confuse future bisects (a human reviewing a failed snapshot named `iPhone15Portrait` on the iPhone 17 sim lane has no way to know whether the 3pt width delta is the cause).
**Fix:** Either (a) update the canvas widths to 393pt (iPhone 17) + 375pt (SE 3) and rename the attachments, or (b) keep the locked layout widths (390/375) but rename the symbols to convey "layout target width," not "device name":
```swift
private static let layoutWidth_390pt: CGFloat = 390  // iPhone 15-class portrait
private static let layoutWidth_375pt: CGFloat = 375  // iPhone SE 3 portrait
// And rename: test_VL_1001_layout390pt_rendersExpected, etc.
```
Same fix shape applies to `EveryoneOnLoadStripViewSnapshotTests.swift`.

### WR-06: Snapshot tests use `traitOverrides.preferredContentSizeCategory` BEFORE the view enters a window — partial trait propagation

**File:** `validationLedgerTests/Loads/Snapshot/ChainOfVouchesViewSnapshotTests.swift:84-89`, `validationLedgerTests/Loads/Snapshot/EveryoneOnLoadStripViewSnapshotTests.swift:80-90`
**Issue:** Both new snapshot suites apply `view.traitOverrides.preferredContentSizeCategory = contentSize` to a free-standing view that has never been added to a window. Per iOS 17 docs, `traitOverrides` propagates through the view hierarchy on the next layout pass, but only for views that participate in a trait collection chain — a window-less view's trait collection is provisional and may not actually reflect the override until first attachment to a window. The `RoleAvatarView` Dynamic Type exception is documented (literal-point-size font), but every other label in `ChainOfVouchesView` and `EveryoneOnLoadStripView` uses `adjustsFontForContentSizeCategory = true` and reads the trait at layout time. If the trait override isn't actually applied, the snapshot renders at the host process's content-size category (typically `.large`), defeating the purpose of the `contentSize` parameter on the helper signature in `ChainOfVouchesViewSnapshotTests.render(...)`.
The Phase 9 `TrustGraphViewSnapshotTests` works around this by setting `traitOverrides` first and then asserting actual rendering, and the WR-04 fix mentioned in the file headers references that pattern — but the new suites do not host the view in a window before layout. If the override silently no-ops, the multi-DTLarge / DTAXXXL coverage promised in the Phase 9 matrix is also at risk on the new suites.
**Fix:** Either (a) host the view in a `UIWindow` before applying the override (matches the production code path), or (b) add an assertion inside the helper that confirms the trait was actually inherited:
```swift
let view = ChainOfVouchesView()
let window = UIWindow(frame: CGRect(origin: .zero, size: CGSize(width: width, height: Self.canvasHeight)))
window.rootViewController = UIViewController()
window.rootViewController?.view.addSubview(view)
view.traitOverrides.preferredContentSizeCategory = contentSize
view.bounds = CGRect(x: 0, y: 0, width: width, height: Self.canvasHeight)
view.configure(chainOfTrust: chain)
view.layoutIfNeeded()
XCTAssertEqual(view.traitCollection.preferredContentSizeCategory, contentSize,
               "Trait override must propagate before layout.")
```
Without (a) or (b), the suite's contentSize parameter is decorative and the WR-04 reference in the file header is misleading.

## Info

### IN-01: Inconsistent `setHighlighted` animation guards between strip chip and tree row

**File:** `validationLedger/Features/Loads/Detail/EveryoneOnLoadStripView.swift:485-500`, `validationLedger/Features/Loads/Detail/ChainOfVouchesView.swift:676-692`
**Issue:** `ChainOfVouchesRowView.setHighlighted` correctly short-circuits the CABasicAnimation when `target == highlightLayer.opacity` (line 678: `if animated && target != highlightLayer.opacity`). `ChipView.setHighlighted` does not — it always creates and adds the animation, even when target equals current opacity (a no-op fade `target → target` that wastes a few microseconds of CoreAnimation work per tap). Same conceptual code, two different implementations. The strip ChipView is also missing `fillMode = .forwards` + `isRemovedOnCompletion = false` (the row variant has both), so the row's animation has explicit fillMode/removal semantics while the chip relies on the post-add model-property assignment to lock the resting state.
**Fix:** Align the two implementations — copy the `if animated && target != highlightLayer.opacity` guard and the explicit fillMode/removal into ChipView, or extract a shared helper `CAShapeLayer.animateOpacity(to:duration:timingName:)` and have both call it.

### IN-02: `composeRowLabel` non-root branch uses force-unwrap of `parentNode!`

**File:** `validationLedger/Features/Loads/Detail/ChainOfVouchesView.swift:437-441`
**Issue:** The non-root branch of `composeRowLabel(node:parentNode:stateCopy:)` force-unwraps `parentNode!` twice for the format-string positional arguments, after the `if parentNode == nil` branch returned. The force-unwrap is logically safe given the nil-check, but mixing optionals + force-unwraps in the same method is a future-foot-gun (a refactor that splits the method or moves the nil-check loses the safety, and the crash would appear only on sparse-chain fallback paths that are easier to miss in code review).
**Fix:** Use `guard let parent = parentNode else { ... }` at the top, returning the root branch, and use `parent` (non-optional) below:
```swift
guard let parent = parentNode else {
    return /* root format */
}
return String(format: /* non-root format */, ..., parent.role.displayName, parent.displayName, stateCopy)
```

### IN-03: `applyLoadedRender` performs a full composition rebuild on every state push, even when geometry hasn't changed

**File:** `validationLedger/Features/Loads/Detail/LoadDetailViewController.swift:1162-1179`
**Issue:** `applyLoadedRender` unconditionally calls `NSLayoutConstraint.deactivate(compositionConstraints); compositionConstraints.removeAll(); buildLayoutForCurrentComposition()` whenever a new `.loaded(load, chainOfTrust)` lands — even when the size class hasn't changed and the banner instance is the same posture as before. Every state push (initial load, pull-to-refresh, post-sheet-dismiss) churns the entire composition geometry: reparents bodyView, rebuilds the iPhoneVerticalTreeContentStack arrangedSubviews, re-installs constraints, re-applies custom spacings. The composition only needs to rebuild when the **banner mounted state** flips (clean → non-clean or vice versa). The current code does it on every fetch.
**Fix:** Guard the rebuild on whether `needsStandaloneBanner` flipped relative to the prior render:
```swift
let priorBannerMount = (chainIntegrityBanner != nil)
// ... existing banner build/destroy ...
if priorBannerMount != needsStandaloneBanner {
    NSLayoutConstraint.deactivate(compositionConstraints)
    compositionConstraints.removeAll()
    buildLayoutForCurrentComposition()
}
```
Not a correctness bug — out of scope for v1 per the review charter — but worth noting because the per-render rebuild bakes in a 16ms+ frame hitch on every pull-to-refresh.

### IN-04: `iPhoneVerticalTreeContentStack` re-parents `bodyView` twice on every iPhone composition build

**File:** `validationLedger/Features/Loads/Detail/LoadDetailViewController.swift:650-653, 694-700`
**Issue:** `buildIPhoneLayoutVerticalTree` first re-parents `bodyView` back to `bodyContainer` (lines 650-653 — defensive against coming from iPad), then immediately removes it again at lines 694-696 and adds it to `iPhoneVerticalTreeContentStack` (line 700). The intermediate `bodyContainer.addSubview(bodyView)` is wasted work — the only correct destination for the iPhone vertical-tree path is `iPhoneVerticalTreeContentStack`. The defensive reparent is left over from copy-paste of the legacy DEBUG path (which DOES want bodyView in bodyContainer).
**Fix:** Skip the intermediate reparent on the vertical-tree path — only the final placement into the content stack matters:
```swift
// Remove from any prior superview (iPad rightPaneContainer, or bodyContainer).
if bodyView.superview != nil {
    bodyView.removeFromSuperview()
}
// (No intermediate addSubview — the addArrangedSubview call below is the final mount.)
```
Eliminate the lines 650-653 block on the vertical-tree path.

### IN-05: `chips` array exposed as `private(set)` but tests reach in via `view.chips` — should be `internal`

**File:** `validationLedger/Features/Loads/Detail/EveryoneOnLoadStripView.swift:158`
**Issue:** `private(set) var chips: [ChipView] = []` marks the setter private and the getter `internal` (default). The unit test `EveryoneOnLoadStripViewTests` reads `view.chips` via `@testable import` — works because `@testable import` exposes internal symbols. The `private(set)` keyword on an `internal` getter is fine, but the file-header comment claims *"Internal access so the unit-test target can iterate via `@testable import`"* — which is misleading because `internal` is the default and `private(set)` is about the setter. Doc/code mismatch.
**Fix:** Update the comment to clarify, or drop the redundant `private(set)` annotation if there's no actual concern about external mutation (the strip rebuilds chips inside `configure(chainOfTrust:)` so external mutation isn't a real risk):
```swift
/// The active set of chip views, in canonical role order. Internal getter
/// (Swift default) so the test target can iterate via `@testable import`.
/// Setter is `private(set)` so external code cannot mutate the array.
private(set) var chips: [ChipView] = []
```
