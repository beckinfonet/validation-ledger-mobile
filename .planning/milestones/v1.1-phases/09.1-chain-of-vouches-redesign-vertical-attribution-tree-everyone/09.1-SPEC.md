# Phase 09.1: Chain-of-Vouches Redesign — vertical attribution tree + everyone-on-load strip — Specification

**Created:** 2026-05-20
**Ambiguity score:** 0.15 (gate: ≤ 0.20)
**Requirements:** 12 locked

## Goal

On iPhone, the chain-of-trust visualization changes from a 2D positioned-node graph (Phase 9 TrustGraphView) to a top-anchored **"Everyone on this load"** dynamic role strip + a **"Chain of vouches"** vertical attribution tree card with a folded chain-integrity footer pill — rendering all 9 existing fixture role-count variants (2 to 6 nodes, including the VL-1009 multi-broker case) at chip-readable typography without the iPhone slot-collision and chip-overcrowding defects the Phase 9 device-UAT pass exposed (debug session `trust-graph-device-bugs`, commit 7337848). The Phase 9 TrustGraphView is preserved unchanged on iPad regular size class.

## Background

Phase 9 (`load-detail-chain-of-trust-graph`, shipped 2026-05-20) introduced TrustGraphView (824 LOC) — a 2D positioned-node + CAShapeLayer-edge visualization with marquee mechanics (gestures, halos, dashed flagged edges, pulse-on-compromised, dim-others). A constraint-propagation timing bug in `layoutSubviews()` (root-caused and fixed during device UAT, commit 7337848) was masking three deeper UX defects on iPhone:

1. The iPhoneSlots role-position table has one slot per `Role`; chains with >1 node sharing a role (VL-1009: 2 brokers) collide at the same slot.
2. The per-node chip composes the Phase 8 `VerificationBadgeView` pill (icon + "VERIFIED" text) plus a 2-line `displayName` at iPhone slot widths of ~70–80pt. The pill alone consumes ~50pt; `displayName` tail-truncates to a single character. User-discovered during device UAT 2026-05-20.
3. The "topology IS the fraud signal" philosophy (D-15 dim-others + dashed flagged edges) requires reading the graph spatially — but at iPhone widths the spatial layout is unreadable, so the fraud signaling collapses.

The `ChainOfTrust` data model (`validationLedger/Core/Load/ChainOfTrust.swift`) already carries the voucher relationships in its `edges: [TrustEdge]` array (`fromPartyID` → `toPartyID`). The reference design's "VIA SHP" / "VIA BRK" attribution suffixes are derivable from this data with no data-model changes — but the design decision locked below uses role-hierarchy (not edge data) for the attribution, see R9. Fixture corpus covers 2 to 6 nodes across 9 fixtures; VL-1009 is the only multi-broker case and its chain-integrity banner explicitly calls out the chameleon-broker re-tender fraud pattern.

The user reviewed a reference design (a vertical attribution tree with SHP/BRK/CAR/DSP/FCT avatar circles, "VIA X" attribution, dashed Y-fork connectors, green "✓ Chain intact" footer pill, and an "Everyone on this load" horizontal strip above) during device UAT 2026-05-20 and committed to the **Big** redesign scope (vs. tiny chip-only fix or chip-refactor-only paths). Captured intent: `.planning/backlog/09.1-chain-of-vouches-redesign.md` (commit c266657).

## Requirements

1. **RoleAvatarView primitive**: A new programmatic UIView that renders a per-role colored circular avatar with a 3-letter role abbreviation centered inside, plus a small status dot at the bottom-right whose color maps from `VerificationState` via a TRUST-02-compliant shared color helper.
   - Current: No avatar primitive exists; verification state is rendered only via the Phase 8 `VerificationBadgeView` pill (icon + text).
   - Target: `validationLedger/UI/Components/RoleAvatarView.swift` exists, programmatically constructed (ARCH-04), parameterized by `role: Role` and `verificationState: VerificationState`, and consumes a single shared color/state helper that `VerificationBadgeView` also consumes (so both primitives cannot drift on the verification color ramp).
   - Acceptance: a unit test renders RoleAvatarView for each of the 5 roles × 4 verification states (20 cases) and asserts the dot color matches the shared helper's output for that state; the same helper is reachable from VerificationBadgeView (single source of truth assertion).

2. **EveryoneOnLoadStripView component**: A horizontally-scrollable strip of role-avatar chips matching the reference design's "Everyone on this load" affordance, rendered **dynamically** — only the roles actually present in the chain appear.
   - Current: No such component; the iPhone Load Detail screen shows only the 2D TrustGraphView.
   - Target: `validationLedger/Features/Loads/Detail/EveryoneOnLoadStripView.swift` exists; the strip's chip count and order match the de-duplicated set of `chainOfTrust.nodes[].role` values in canonical role order (Shipper → Broker → Carrier → Dispatch → Factoring). A trailing "All watching live" meta caption is rendered at the right edge.
   - Acceptance: snapshot tests cover VL-1003 (2 nodes → 2 chips), VL-1005 (3 nodes → 3 chips), VL-1007 (4 nodes → 4 chips), VL-1001 (5 nodes → 5 chips), and VL-1009 (6 nodes / 5 distinct roles → 5 chips — duplicate broker collapses to one strip slot but renders as two siblings in the tree per R9).

3. **ChainOfVouchesView component**: A vertical attribution tree card replacing the 2D trust graph on iPhone, with per-node rows showing avatar + role-name + "VIA X" attribution + party `displayName`, connected by dashed lines and Y-fork connectors for sibling roles.
   - Current: No vertical tree component; chain-of-trust is rendered only by `TrustGraphView` (2D positioned nodes + CAShapeLayer edges).
   - Target: `validationLedger/Features/Loads/Detail/ChainOfVouchesView.swift` exists; renders the chain as a top-anchored vertical hierarchy SHP (ROOT) → BRK (VIA SHP) → CAR (VIA BRK) → {DSP, FCT} (both VIA CAR); attribution suffix is computed from a fixed role-parent table (R9 details).
   - Acceptance: snapshot tests for the 5 representative fixtures (VL-1001/1005/1007/1009/1010) render the tree with role-hierarchy ordering and "VIA X" suffixes verified per node; a unit test asserts the attribution suffix for each row matches the role-hierarchy table for that role.

4. **Chain-integrity footer fold-in**: The Phase 9 standalone `ChainIntegrityBannerView` is preserved as a component but is no longer placed above the chain visualization on iPhone — it is rendered as a footer pill inside the ChainOfVouchesView card, mirroring the reference's "✓ Chain intact · 4 vouches, no anonymous parties" or "⚠ Chain compromised: …" placement.
   - Current: `ChainIntegrityBannerView` renders as a top-of-screen banner above the trust graph.
   - Target: On iPhone, the card contains a footer pill (tinted green for `.clean`, red/destructive for `.compromised`, yellow/caution for `.flagged`) with the integrity verdict copy. The standalone top-of-screen banner is removed from the iPhone scroll order. The component file itself is preserved; only its mounting location changes on iPhone.
   - Acceptance: snapshot tests confirm no banner above the title bar in the iPhone Load Detail layout for any of the 5 representative fixtures; chain-compromised fixtures (VL-1009, VL-1010) render the verdict pill inside the card footer with the correct color and copy.

5. **Size-class routing in LoadDetailViewController**: The iPhone path renders the new strip + tree; the iPad regular size class continues to render `TrustGraphView` unchanged.
   - Current: `LoadDetailViewController` constructs `TrustGraphView` for both iPhone and iPad code paths.
   - Target: `LoadDetailViewController.buildIPhoneLayout` (and the corresponding iPad layout method) instantiate distinct subviews — iPhone gets `EveryoneOnLoadStripView` + `ChainOfVouchesView`; iPad continues to instantiate `TrustGraphView` (preserved untouched). The CR-02 reparenting fix from yesterday's code-review-fix extends to handle the new iPhone children.
   - Acceptance: UI test on iPad regular width class (e.g., iPad mini portrait + landscape) confirms TrustGraphView is visible and renders correctly; UI test on iPhone confirms TrustGraphView is NOT in the view hierarchy and the new components ARE; rotation iPad↔iPhone (Slide Over) preserves layout without crash.

6. **A11y rewrite (D-22 supersedure)**: The Phase 9 D-22 container-with-ordered-elements VoiceOver model is replaced on iPhone by a leaf-element model — each strip chip and each tree row is its own accessibility element with a composed label.
   - Current: On iPhone, `TrustGraphView` is `isAccessibilityElement = false` and publishes an ordered `accessibilityElements` array of node + edge-companion views (Phase 9 D-22).
   - Target: On iPhone, neither the strip nor the tree container is an accessibility element; each strip chip's `accessibilityLabel` is `"<RoleName>, <DisplayName>, <verification-state-copy>"` (e.g., "Broker, FreightWise Brokerage, verified"); each tree row's label additionally includes the voucher (e.g., "Broker FreightWise Brokerage, vouched by Shipper Global Exports, verified"). Implicated rows append the implicated-suffix per UI-SPEC line 845. On iPad, the Phase 9 D-22 model is preserved unchanged (TrustGraphView still ships with its container model).
   - Acceptance: a new `ChainOfVouchesViewAccessibilityTests` suite asserts each chip and each tree row exposes the composed label as an individual leaf for the 5 representative fixtures; the existing Phase 9 D-22 accessibility tests for TrustGraphView remain green (iPad path).

7. **D-15 supersedure (topology no longer encodes fraud)**: The Phase 9 D-15 "dim-others" mechanic and the dashed-flagged-edges visual treatment do not propagate to ChainOfVouchesView; on iPhone, the chain-integrity footer pill (R4) is the sole fraud signal carrier. Tree topology is purely organizational.
   - Current: Phase 9 D-15 dims non-implicated nodes at 50% alpha when chain is non-clean; flagged edges render dashed; pulse halo wraps the implicated node.
   - Target: On iPhone, all tree rows render at full alpha regardless of chain integrity verdict; no dashed connectors; no pulse halo. The chain-integrity footer pill carries the entire fraud-signaling burden via verdict copy + tint. On iPad, D-15 is preserved unchanged in TrustGraphView.
   - Acceptance: snapshot tests for compromised fixtures (VL-1009, VL-1010) on iPhone show full-alpha rows for the implicated node alongside non-implicated; the implicated node is identifiable only via the footer copy (no visual treatment on the row itself); iPad snapshot tests for the same fixtures still show dimmed non-implicated nodes.

8. **iPhone scroll order**: On iPhone, the EveryoneOnLoadStripView + ChainOfVouchesView card are placed ABOVE the load-detail body (status timeline, cargo, agreed rate, BOL number, ETA); on iPad the body layout is unchanged.
   - Current: On iPhone, `TrustGraphView` sits inside the body container at its existing position (determined by Phase 9 `LoadDetailBodyView`).
   - Target: On iPhone, the scroll order from top to bottom is: [limited-trust banner] → [REF-XXXX title + route summary] → [EveryoneOnLoadStripView] → [ChainOfVouchesView card with integrity footer pill] → [status timeline pills] → [cargo / agreed rate / BOL number / ETA].
   - Acceptance: a snapshot test of the full iPhone Load Detail scroll content confirms the documented vertical order; a `LoadDetailBodyView` unit test asserts the subview order.

9. **Multi-broker forced-sibling rule**: When the chain has multiple nodes sharing a role (e.g. VL-1009: two brokers), the tree renders all such nodes as **siblings** under the role-hierarchy parent, regardless of the actual `edges[].fromPartyID` data. The "VIA X" attribution suffix uses the role-hierarchy table: BRK → "VIA SHP", CAR → "VIA BRK", DSP → "VIA CAR", FCT → "VIA CAR".
   - Current: The Phase 9 TrustGraphView positions multi-broker nodes at the same iPhoneSlots coordinate (collision); after the 7337848 fix they no longer stack at origin but still collide at the slot table position.
   - Target: ChainOfVouchesView's row layout uses a fixed role-parent table to compute attribution. For VL-1009: BRK FreightWise and BRK Keystone both render as siblings under SHP with "VIA SHP" suffix; the fraud (chameleon re-tender from `edges` data) is conveyed by the chain-integrity footer pill copy alone, not by tree topology.
   - Acceptance: a unit test passes VL-1009's `ChainOfTrust` into ChainOfVouchesView's tree-builder and asserts both broker rows are siblings under the shipper row with attribution "VIA SHP"; a snapshot test confirms the visual.

10. **TrustGraphView preservation on iPad**: Phase 9 `TrustGraphView`, `TrustNodeView`, `ChainIntegrityBannerView` (as a top banner on iPad), and all associated tests (TrustGraphView{Layout,Accessibility,Gesture,Snapshot} + TrustNodeView{Gesture,Snapshot}) remain in the codebase and continue to render on iPad without regression.
   - Current: All Phase 9 components are mounted on both iPhone and iPad code paths in LoadDetailViewController.
   - Target: Phase 9 components are still compiled, tested, and instantiated on the iPad regular-width path (`UIUserInterfaceSizeClass.regular`); their tests stay green.
   - Acceptance: all 32 Phase 9 trust-graph tests (per the `trust-graph-device-bugs` verification list) continue to pass on iPad simulator; a UI test on iPad regular width class confirms TrustGraphView renders for all 5 representative fixtures.

11. **ChainOfTrust data model unchanged**: Phase 9.1 does NOT modify `ChainOfTrust`, `TrustNode`, `TrustEdge`, `ChainIntegrity`, `PriorRelationship`, or any other data-layer types. All new components consume the existing data model.
   - Current: Data layer is defined by Phase 7+9 (`Core/Load/ChainOfTrust.swift` + neighbors).
   - Target: Zero changes to any file under `validationLedger/Core/Load/` for trust types. The new view components read fields off existing types.
   - Acceptance: `git diff` from the 9.1 branch-point to the 9.1 completion commit shows zero changes to `validationLedger/Core/Load/{ChainOfTrust,TrustNode,TrustEdge,ChainIntegrity,PriorRelationship}.swift`.

12. **TRUST-02 single-source-of-truth lock preserved**: The verification color ramp lives in exactly one place; RoleAvatarView and VerificationBadgeView both consume that one place. No parallel color-ramp lookup tables.
   - Current: `VerificationBadgeView` owns the verification color ramp inline.
   - Target: The verification color ramp is extracted to a `DS.Colors.Verification` (or similar TBD in /gsd-ui-phase 9.1) namespace that BOTH `VerificationBadgeView` and the new `RoleAvatarView` consume. Adding a parallel implementation would fail a negative grep gate.
   - Acceptance: a negative grep gate asserts that `VerificationState` case mapping to a `UIColor`/`CGColor` occurs in EXACTLY one source file (the shared helper); RoleAvatarView and VerificationBadgeView both reference that file. The TRUST-02 lock comment in `VerificationBadgeView.swift` is preserved or relocated to the shared helper.

## Boundaries

**In scope:**
- New component: `RoleAvatarView.swift` (R1)
- New component: `EveryoneOnLoadStripView.swift` (R2)
- New component: `ChainOfVouchesView.swift` (R3) — vertical attribution tree with role-hierarchy-based "VIA X" attribution
- Fold `ChainIntegrityBannerView` mounting on iPhone into the new card footer pill (R4) — component itself unchanged
- `LoadDetailViewController` size-class routing — iPhone uses new components, iPad keeps TrustGraphView (R5)
- Full a11y rewrite for new iPhone components (R6) — leaf-element model
- iPhone scroll-order change: chain block above body (R8)
- New shared verification color helper consumed by RoleAvatarView + VerificationBadgeView (R12)
- Snapshot + unit + UI tests for all 5 representative fixtures across both iPhone and iPad paths

**Out of scope:**
- 2D trust graph changes on iPad — preserved unchanged per user decision (R5, R10).
- `ChainOfTrust` / `TrustNode` / `TrustEdge` / `ChainIntegrity` / `PriorRelationship` data-model changes — explicitly forbidden (R11) so 9.1 doesn't drag in Phase 7 type churn.
- Presence indicators / "All watching live" realtime substrate — the strip carries the static "All watching live" caption text only; no realtime subscription wiring (M3 milestone).
- Animation / transition polish (strip-tap → tree-row highlight) — design polish deferred to a separate UI iteration.
- Push notifications for chain-integrity changes — separate M3 milestone.
- iPad-specific layout adjustments (rotation, split-view changes) — explicitly preserved as-is; Phase 9's iPad layout is the contract.
- Edge-data-driven "VIA X" attribution — explicitly superseded by role-hierarchy attribution (R9); the actual `edges` from-side is consulted ONLY by the chain-integrity computation that drives the footer pill (R4).
- TRUST-02 lock changes to `VerificationState` enum upstream — the enum stays; only the color-ramp implementation moves to a shared helper (R12).

## Constraints

- **TRUST-02 lock preserved** — exactly one verification color-ramp source (R12). Negative grep gate locks this.
- **No `ChainOfTrust` data model changes** — Phase 7 contract is sacrosanct for 9.1 (R11).
- **`-MockKYCStatusVerified` pattern precedent** — if 9.1 needs any DEBUG-only toggles (e.g., for switching between strip-only / tree-only / both for marketing screenshots), they MUST follow the `-MockKYCStatusVerified` launch-arg precedent established 2026-05-20.
- **Phase 9 iPad TrustGraphView is unchanged** — R10. The new components are siblings, not replacements.
- **Test runner discipline** — verification uses the scoped serial simulator-lane (`-skip-testing:validationLedgerDeviceTests -parallel-testing-enabled NO`); never bare `xcodebuild test` (project memory `ios-test-suite-pitfalls`).
- **Atomic-commit convention** — `fix(09.1):` / `feat(09.1):` / `test(09.1):` / `chore(09.1):` per project precedent.
- **gsd-sdk polyfill** — every `gsd-sdk query …` Bash call prefixes `NODE_OPTIONS="--require /tmp/structured-clone-polyfill.js"` (project memory `gsd-sdk-node16-workaround`).
