key-decisions:
  - "ChainOfVouchesRowView + ChainOfVouchesFooterPillView are TOP-LEVEL public final classes within ChainOfVouchesView.swift, NOT private nested classes on ChainOfVouchesView. Rationale: the planner explicitly wanted public `rowViews(for:) -> [ChainOfVouchesRowView]` API for Plan 05's scroll-anchor frame access — that requires the row type to be public. The footer pill is exposed similarly so the unit tests can introspect via @testable. Plan 03's EveryoneOnLoadStripView nests its ChipView privately because no external consumer needs the chip type; the row + footer pill have external consumers (the tests in Plan 04, the VC in Plan 05)."
  - "Y-fork connector path recomputation lives in ChainOfVouchesRowView.layoutSubviews, NOT in the container's layoutSubviews. Rationale: each row owns its own connector layer; the path runs from the parent row's avatar bottom-center to this row's avatar top-center, computed in the parent stack's coordinate space via `parent.avatar.convert(_:to: parentSuperview)`. When a parent row's bounds change (Dynamic Type), this row's layoutSubviews doesn't fire automatically — but the container's traitCollectionDidChange triggers setNeedsLayout, which cascades."
  - "Per-row connector layer is INSERTED INTO THE PARENT STACK'S LAYER (parentSuperview.layer.insertSublayer(connectorLayer, at: 0)), NOT into the row's own layer. Mirrors TrustGraphView's pattern of placing edge layers in `contentContainer.layer` (Phase 9 line 349). Rationale: the connector geometry spans the inter-row gap; if it lived in the row's layer, the segment outside the row's bounds would be clipped (when `masksToBounds = true`) or rendered ambiguously (when false)."
  - "The `composeRowLabel(node:parentNode:stateCopy:)` helper takes three arguments and lives at the container level (NOT on the row). Reason: the row doesn't know its parent's TrustNode (it only knows the parent ROW via a weak ref). The container CAN look up `row.parentRow?.node` because it built both rows. Computing + assigning the label at container build time also means the row's `accessibilityLabel` is set BEFORE the row is added to the tree stack — XCTest introspection via `treeStack.arrangedSubviews` finds the labels immediately."
  - "No implicated-row a11y suffix is appended. SPEC R6 references 'UI-SPEC line 845' for an implicated suffix, but UI-SPEC.md ends at line 407 and locks no implicated suffix; R7 forbids any row-level fraud signaling on iPhone (footer pill is the sole fraud signal). Omitting the suffix is the consistent interpretation across both spec layers. The PLAN's Task 1 `<action>` block calls this out explicitly."
  - "Footer pill `apply(verdict:reason:)` always assigns a fresh accessibility label and pill text — there is no .clean short-circuit. Phase 9 ChainIntegrityBannerView hides on .clean; the 9.1 folded pill MUST render on .clean because the affirmative cadence is the trust signal. Pattern guidance for future plans: when a plan's acceptance regex matches a single-line constructor form, the declaration should be single-line even if the line is wider than the project's usual wrap point."

  - "Y-fork connector geometry is the 3-segment elbow (move parentBottomCenter -> vertical to midY -> horizontal to myCenter.x -> vertical to myTopCenter). For straight-down case (single child), parentCenter.x == myCenter.x and the horizontal segment has zero length — the path looks vertical. For sibling case (VL-1009 SHP -> {BRK1, BRK2}), the segment widths differ. Both broker rows draw their OWN connector; the duplicated upper segment overlays invisibly (same stroke, same dash, same color). This is cleaner than coordinating segment ownership across siblings."

patterns-established:
  - "Pattern 11: Per-row CAShapeLayer connector attached to the parent stack's layer with Y-fork geometry recomputed in row.layoutSubviews. The pattern handles both straight-down and sibling-fork cases through the same elbow code path (the elbow degenerates to a straight line when parent and child x-centers coincide). Applicable to any vertical tree where rows can have multiple siblings (e.g. a future per-edge attribution view, or a tree-of-handoffs visualization)."
  - "Pattern 12: B2 a11y wiring — when a leaf-element view's composed label depends on parent-of-leaf data (e.g. 'vouched by <parent's role + name>'), compute + assign the label IN THE CONTAINER's row-builder rather than IN THE ROW. ## Decisions Made

- **ChainOfVouchesRowView + ChainOfVouchesFooterPillView are top-level public final classes**, NOT private nested classes. Rationale: the public `rowViews(for:) -> [ChainOfVouchesRowView]` API surface in Plan 04 forces the row type to be public so Plan 05's VC can iterate the returned rows + compute scroll-anchor frames. The footer pill is exposed similarly so unit tests can introspect via `view.footerPill.backgroundColor` / `view.footerPill.pillLabel.text` / `view.footerPill.accessibilityLabel`. Plan 03's EveryoneOnLoadStripView nests its ChipView privately because no external consumer needs the chip type; the row + footer pill have external consumers.
- **Per-row CAShapeLayer connector inserted into the PARENT stack's layer, not the row's own layer.** Mirrors `TrustGraphView`'s pattern of placing edge layers in `contentContainer.layer` (Phase 9 line 349). If the connector lived in the row's layer, the segment crossing the inter-row gap would either be clipped (when `masksToBounds = true`) or render ambiguously (when false). Container-level placement also makes the Y-fork geometry trivial — both broker rows in VL-1009 draw their own elbow up to the shared SHP row, and the duplicated upper segment overlays invisibly with the same stroke/dash/color.
- **Connector path computed in the parent stack's coordinate space via `parent.avatar.convert(_:to:)`.** The convert API walks the ancestor chain so the path stays correct even if the parent stack reparents (currently never happens in 9.1, but future-proofs the design). The path is recomputed in `row.layoutSubviews()` so Dynamic Type changes re-path automatically once the container's `traitCollectionDidChange` cascades a `setNeedsLayout()`.
- **`composeRowLabel(node:parentNode:stateCopy:)` lives at the container level**, not on the row. Reason: a row knows its parent ROW via a weak ref, but it doesn't know the parent's TrustNode — only the container knows both. The container looks up `row.parentRow?.node` and passes it into the helper. Container-level assignment also means the label is on the row BEFORE the row is added to the tree stack — XCTest introspection via `treeStack.arrangedSubviews` finds the label immediately, which is the B2 wiring intent.
- **No implicated-row a11y suffix appended.** SPEC R6 references "UI-SPEC line 845" for an implicated suffix, but UI-SPEC.md ends at line 407 and locks no implicated suffix; R7 forbids any row-level fraud signaling on iPhone (footer pill is the sole fraud signal). Omitting the suffix is the consistent interpretation across both spec layers. The PLAN's Task 1 `<action>` block calls this out explicitly. The composed row labels follow the UI-SPEC §Accessibility Contract templates verbatim: root row -> `"<RoleDisplayName> <displayName>, root of the chain, <stateCopy>"`; non-root row -> `"<RoleDisplayName> <displayName>, vouched by <ParentRoleDisplayName> <ParentDisplayName>, <stateCopy>"`.
- **Footer pill `apply(verdict:reason:)` always assigns fresh visuals + a11y label.** There is no `.clean` short-circuit. Phase 9 ChainIntegrityBannerView hides on `.clean`; the 9.1 folded pill MUST render on `.clean` because the affirmative cadence ("Chain intact . N vouches, no anonymous parties") IS the trust signal. The R4 binding test in `ChainOfVouchesViewTests.test_footerPill_renders_for_cleanVerdict_withGreenTint` asserts: (i) pill is not hidden, (ii) background alpha is in the soft-tint range [0.1, 0.3], (iii) pillLabel text contains "Chain intact".
- **`vl1005_threeRolesClean` factory carries `.caution` verdict despite "Clean" in its name** (Plan 03 factory naming convention). The matching JSON fixture VL-1005 also carries `.caution`. The plan's Task 3 Step A lists VL-1005 among the "clean-verdict fixtures" targeted for the affirmative-cadence reason text; this is a documentation slip in the plan (NOT a contradiction the executor must resolve). The fixture-text edit applies to all 4 listed fixtures regardless of verdict (the gate is purely a text-content check). The factory verdict for VL-1005 stays `.caution` so the snapshot test exercises the yellow footer pill tier; the JSON fixture's reason text changes to "2 vouches, no anonymous parties" as the plan instructed.
- **Y-fork connector elbow degenerates to a straight line for single-child cases.** When `parentBottomCenter.x == myTopCenter.x` (single-child case, the typical chain), the elbow's horizontal segment has zero length and the path reads as a single vertical dashed line. For sibling cases (VL-1009 SHP -> {BRK1, BRK2}), the segment widths differ. Both broker rows draw their OWN connector; the duplicated upper segment overlays invisibly with the same stroke/dash/color. Cleaner than coordinating segment ownership across siblings.
- **AttributionParents enum is `fileprivate`**, NOT `private`. Reason: it's referenced by both `ChainOfVouchesView.buildRows(from:)` (the container) and the nested types. `fileprivate` is the appropriate scope; `private` would prevent the container method from reaching the nested enum's static members. The lookup walks UP the canonical hierarchy via a `while let parent = canonical[current] { if presentRoles.contains(parent) { return parent }; current = parent }; return nil` loop — handles sparse-chain attribution-fallback in a tight 4-line idiom.
- **Acceptance grep #5 (`RoleAvatarView\\(.*variant: \\.tree`) required a single-line constructor.** My initial implementation declared the row's avatar across 3 lines (`let avatar: RoleAvatarView = RoleAvatarView(\n    role: .shipper, state: .verified, variant: .tree\n)`); the regex didn't match. Collapsing to a single line satisfied the gate without changing semantics. Pattern guidance for future plans: when a plan's acceptance regex matches a single-line constructor form, the declaration should be single-line even if the line is wider than the project's usual wrap point. (This same fix appeared in Plan 03 — Pattern 7-ish "regex-form vs. call-site form" — and is generalising.)
