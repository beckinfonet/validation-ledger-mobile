# Phase 09.1: Chain-of-Vouches Redesign — Research

**Researched:** 2026-05-20
**Domain:** Native iOS / UIKit — vertical attribution tree + dynamic role-chip strip on iPhone; iPad TrustGraphView preservation; shared verification color-ramp extraction; DEBUG-only render-path toggle; size-class routing; snapshot baseline re-record posture.
**Confidence:** HIGH (every recommendation is grounded in existing in-repo precedents — Phase 7/8/9 — or in the iOS 17 SDK already deployed elsewhere in the codebase. Zero new SwiftPM dependencies. No third-party docs needed.)

## Summary

Phase 9.1 is a **pure UIKit composition refactor** with one structural extraction (`DS.Colors.Verification`), one new primitive (`RoleAvatarView`), two new feature views (`EveryoneOnLoadStripView`, `ChainOfVouchesView`), three modified files (`VerificationBadgeView`, `Colors`, `LoadDetailViewController`), and one DEBUG-only launch arg (`-Mock2DTrustGraphOnIPhone`). **No new dependencies, no data-model changes, no protocol abstractions.** Every recommendation in this document compounds against an existing in-repo precedent the planner can `git grep` for.

The largest design risk — that the planner re-opens locked decisions in CONTEXT.md or invents pattern abstractions — is mitigated by treating the SPEC + CONTEXT + UI-SPEC trio as authoritative and confining this document to **implementation recommendations within the locked design space**. Where alternatives exist (Y-fork geometry, attribution-table location, size-class trait API), this document names them and recommends one with rationale; where the spec has locked a decision (color ramp namespace, leaf-element a11y model, scroll order), this document gives the cleanest implementation of the locked decision.

**Primary recommendation:** Build the tree as a vertical `UIStackView` of `ChainOfVouchesRowView`s with **per-row `CAShapeLayer` connectors drawn in `layoutSubviews()`** (mirrors `TrustGraphView` precedent for edge geometry). Place the attribution-parent table as a `private static let` on `ChainOfVouchesView`'s tree-builder. Use the iOS 17 `registerForTraitChanges(_:handler:)` API for size-class routing (precedent: `traitOverrides` already used in `TrustGraphViewSnapshotTests.swift:63`). For D-05 snapshot re-record, **the work is much smaller than CONTEXT implies**: snapshot tests in this codebase are **attachment-only** (`UIKitSnapshot.attach`) with **no on-disk reference images** — there are no baselines to delete; the work is restricting test bounds to iPad sizes and updating the attachment names. This finding should be surfaced to the planner immediately.

### Pattern 1: Per-Row CAShapeLayer Connector (§1 — Y-Fork Geometry)

**What:** Each `ChainOfVouchesRowView` owns its own `CAShapeLayer` connector that draws the dashed line FROM the parent row's avatar TO this row's avatar. For sibling-fork cases (CAR→{DSP,FCT} or VL-1009's SHP→{BRK,BRK}), each child row's layer draws an independent Y-segment from the shared parent's bottom-center.

**When to use:** Any vertical tree where rows resize independently with Dynamic Type or rotation. Locked here by R3 + UI-SPEC line 243.

**Comparison of alternatives:**

| Approach | Pros | Cons | Verdict |
|----------|------|------|---------|
| (a) **Per-row CAShapeLayer + UIBezierPath** | Local re-path on row resize; matches `TrustGraphView` precedent (`edgeLayers: [CAShapeLayer]` at line 117); deterministic dash phase; no cross-row coupling | Slightly more layers in the hierarchy (N-1 layers for N rows) — but tree max is 6 rows in the fixture corpus, so worst case is 5 layers | ✅ **Recommended** |
| (b) Single tree-wide CAShapeLayer overlay | One layer = one re-path per layout pass | EVERY row resize triggers full re-path; rows must publish their avatar center via delegation back up to the tree; sibling-group geometry encoded in single path = harder to test | ❌ rejected — coupling and full re-path |
| (c) UIView-based line subviews + cornerMask | Easier to test pixel-wise | Dashed line via UIView requires `layer.mask = CAShapeLayer` anyway (same layer dependency, more bookkeeping); right-angle Y-fork bend is a 3-segment composition of subviews (parent vertical, fork bar, two child verticals) per row = more views than approach (a) | ❌ rejected — same dependency, more views |

**Geometry (code-sized sketch — ~25 LOC):**

```swift
// In ChainOfVouchesRowView. parentAnchor is set by the tree-builder.
// Owns its own dashed connector that runs from the parent row's avatar
// bottom-center to THIS row's avatar top-center.
private let connectorLayer: CAShapeLayer = {
    let l = CAShapeLayer()
    l.strokeColor = DS.Colors.separator.cgColor
    l.lineWidth = 1.5
    l.lineDashPattern = [3, 3]
    l.fillColor = nil
    return l
}()

// Set once by ChainOfVouchesView when the tree is built.
weak var parentRow: ChainOfVouchesRowView?

override func layoutSubviews() {
    super.layoutSubviews()
    guard let parent = parentRow,
          let parentSuperview = parent.superview,
          parentSuperview === self.superview else {
        connectorLayer.path = nil
        return
    }
    // Geometry in the SHARED parent-stack coordinate space (the vertical
    // UIStackView holding all rows). superview === parentSuperview asserted
    // above guarantees both row frames live in the same space.
    let parentBottomCenter = CGPoint(
        x: parent.frame.midX,                            // sibling fork: this is the parent's center
        y: parent.frame.maxY - parent.layoutMargins.bottom
    )
    let myTopCenter = CGPoint(
        x: self.frame.midX,
        y: self.frame.minY + self.avatar.frame.midY
    )
    // For straight-down case (single child): parentBottomCenter.x == myTopCenter.x
    // For Y-fork case (sibling): they differ; draw vertical-down-then-horizontal-
    // then-vertical-down 3-segment path (i.e. an "elbow" — UI-SPEC §Y-fork).
    let midY = (parentBottomCenter.y + myTopCenter.y) / 2
    let path = UIBezierPath()
    path.move(to: parentBottomCenter)
    path.addLine(to: CGPoint(x: parentBottomCenter.x, y: midY))  // vertical down to fork bar
    path.addLine(to: CGPoint(x: myTopCenter.x, y: midY))         // horizontal to child's x
    path.addLine(to: myTopCenter)                                 // vertical down to child's top
    connectorLayer.path = path.cgPath
    if connectorLayer.superlayer == nil {
        parentSuperview.layer.insertSublayer(connectorLayer, at: 0)
    }
}
```

**Key insight:** The connector layer is inserted into the **parent stack's layer** (not the row's own layer), because the geometry spans from parent row's frame to this row's frame — both of which are children of the same vertical UIStackView. This mirrors `TrustGraphView` placing edge layers in `contentContainer.layer` rather than in any node's layer (TrustGraphView.swift:349). When the parent row's bounds change (Dynamic Type), this row's `layoutSubviews` doesn't fire — so the tree-builder publishes a `setNeedsLayout()` on every child row after every parent layout pass; cheap (N ≤ 6).

**Alternative for the root row:** the root row's `parentRow` is nil; `connectorLayer.path = nil` in that case (no connector above the root). UI-SPEC line 252 confirms the root carries `"ROOT"` text in place of `"VIA X"`.

### Pattern 2: Vertical UIStackView with Per-Row Layout (§2)

**What:** `ChainOfVouchesView` holds a vertical `UIStackView` (`axis = .vertical`, `spacing = DS.Spacing.md`, `alignment = .fill`) of `ChainOfVouchesRowView` instances. Sibling rows (CAR→{DSP,FCT}; VL-1009 SHP→{BRK,BRK}) are **two separate rows in the stack at adjacent indices** — NOT a horizontal sub-stack.

**When to use:** Locked by SPEC R9 — "tree renders all such nodes as siblings under the role-hierarchy parent" — and by UI-SPEC line 238 "Tree row vertical spacing inter-row gap: `DS.Spacing.md`". The connector layer (Pattern 1) handles the visual Y-fork; the stack just sequences rows in depth-first order.

**Why not a horizontal sub-stack for siblings?** Two reasons:
1. **Highlight semantics.** D-10 says tapping the BRK chip lights BOTH broker rows. If siblings were horizontal, the highlight outline would have to span a horizontal pair — more complex than two independent per-row outlines.
2. **Scroll anchoring.** D-08 scrolls to the first matching row + makes the sibling-group visible. A vertical stack with sibling rows at adjacent indices means "scroll to the first" naturally puts both on-screen (they're stacked above-and-below each other in screen space within ~2pt).

**Tree-builder algorithm (code-sized sketch — ~30 LOC):**

```swift
// In ChainOfVouchesView. Builds the depth-first row sequence.
private func buildRows(from chain: ChainOfTrust) -> [ChainOfVouchesRowView] {
    var rows: [ChainOfVouchesRowView] = []
    var rowsByRole: [Role: [ChainOfVouchesRowView]] = [:]

    // Canonical role order is the depth-first walk order (SHP → BRK → CAR → DSP → FCT).
    // Within a role, nodes are sorted by partyID alphabetical (UI-SPEC line 300 —
    // determinism for VoiceOver order and snapshot stability).
    let roleOrder: [Role] = [.shipper, .broker, .carrier, .dispatch, .factoring]
    for role in roleOrder {
        let nodes = chain.nodes
            .filter { $0.role == role }
            .sorted { $0.partyID < $1.partyID }
        for node in nodes {
            let row = ChainOfVouchesRowView()
            // Attribution: walk UP the canonical hierarchy until a present
            // role is found. Forces siblings under the same parent (R9).
            let parentRole = Self.attributionParent(for: role, presentRoles: Set(chain.nodes.map { $0.role }))
            let attributionText: String
            if let pr = parentRole {
                attributionText = String(
                    format: NSLocalizedString("loads.detail.chain.9_1.row.attribution.format",
                                              value: "VIA %@", comment: "9.1 tree-row attribution suffix"),
                    pr.shortAbbreviation  // "SHP", "BRK", "CAR", "DSP", "FCT" — see §5
                )
            } else {
                attributionText = NSLocalizedString("loads.detail.chain.9_1.row.attribution.root",
                                                    value: "ROOT", comment: "9.1 root row attribution")
            }
            row.configure(node: node, attributionText: attributionText)
            // Parent row pointer (Pattern 1): first row in parentRole's bucket.
            row.parentRow = parentRole.flatMap { rowsByRole[$0]?.first }
            rows.append(row)
            rowsByRole[role, default: []].append(row)
        }
    }
    return rows
}
```

### Pattern 3: Strip → Tree Scroll Anchoring (§3)

**What:** `LoadDetailViewController` owns the outer `UIScrollView` (the Load Detail scroll content). On chip tap, the VC:
1. Asks `ChainOfVouchesView` for the row-views matching the tapped role.
2. Converts the first matching row's frame to the outer scroll view's coordinate space.
3. Calls `outerScrollView.scrollRectToVisible(_:animated: true)` with the rect inset by `DS.Spacing.md` on top.
4. Tells `ChainOfVouchesView` to apply the highlight outline to ALL matching rows.

**When to use:** Locked by D-08, D-09, D-10. The pattern keeps scroll knowledge OFF the tree (the tree has no reference to the outer scroll) and OFF the strip (the strip just publishes the tap event).

**Coordinate conversion (code-sized sketch — ~15 LOC):**

```swift
// In LoadDetailViewController. Called by EveryoneOnLoadStripView.onRoleTap.
private func handleStripChipTap(role: Role) {
    let matchingRows = chainOfVouchesView.rowViews(for: role)
    guard let firstRow = matchingRows.first else { return }

    // Convert the first matching row's frame from the tree's coord space
    // up to the outer scroll view's content space. UIKit's convert(_:to:)
    // walks the ancestor chain — works regardless of how deeply nested the
    // tree is inside cards / stacks / containers.
    let rectInScroll = firstRow.convert(firstRow.bounds, to: outerScrollView)
    // Inset top by sm so the row doesn't hug the very edge of the visible
    // area. For VL-1009 (sibling brokers), the second sibling row sits
    // immediately below the first — scrollRectToVisible naturally brings
    // both into view at this inset.
    var target = rectInScroll.insetBy(dx: 0, dy: -DS.Spacing.sm)
    target.origin.y -= DS.Spacing.md  // leave top breathing room
    outerScrollView.scrollRectToVisible(target, animated: true)

    // Apply highlight (Pattern 4) and haptic.
    chainOfVouchesView.applySelectedRole(role)
    everyoneOnLoadStripView.applySelectedRole(role)
    UISelectionFeedbackGenerator().selectionChanged()
}
```

**Key insight:** `convert(_:to:)` is the right primitive — it traverses the view hierarchy without needing to know the intermediate ancestors. If the planner later splits ChainOfVouchesView into a subdirectory or adds wrapping containers, this code still works without modification.

### Pattern 4: Highlight Outline (D-11)

**What:** Each `ChainOfVouchesRowView` and each strip chip owns a `CAShapeLayer` for the 2pt outline. On `applySelectedRole`, the layer fades in over 120ms via `UIView.animate`; after 1.8s hold (configurable per-row, sticky until next selection), the outline fades out over 200ms. Sticky variant chosen per UI-SPEC line 218.

**Implementation pattern (code-sized sketch — ~20 LOC):**

```swift
// In ChainOfVouchesRowView.
private let highlightLayer: CAShapeLayer = {
    let l = CAShapeLayer()
    l.strokeColor = DS.Colors.primary.cgColor
    l.lineWidth = 2.0
    l.fillColor = nil
    l.opacity = 0
    return l
}()

override func layoutSubviews() {
    super.layoutSubviews()
    let insetRect = bounds.insetBy(dx: 4, dy: 4)
    highlightLayer.path = UIBezierPath(roundedRect: insetRect, cornerRadius: 12).cgPath
    if highlightLayer.superlayer == nil { layer.addSublayer(highlightLayer) }
}

func setHighlighted(_ on: Bool, animated: Bool = true) {
    let duration: TimeInterval = on ? 0.12 : 0.20
    let target: Float = on ? 1.0 : 0.0
    if animated {
        let fade = CABasicAnimation(keyPath: "opacity")
        fade.fromValue = highlightLayer.opacity
        fade.toValue = target
        fade.duration = duration
        fade.timingFunction = CAMediaTimingFunction(
            name: on ? .easeOut : .easeIn)
        fade.fillMode = .forwards
        fade.isRemovedOnCompletion = false
        highlightLayer.add(fade, forKey: "highlight")
    }
    highlightLayer.opacity = target
}
```

The `ChainOfVouchesView.applySelectedRole(_:)` iterates `rowViews`, calls `setHighlighted(true)` on matching rows and `setHighlighted(false)` on non-matching. The 1.8s hold + fade-out is driven from the VC via `DispatchQueue.main.asyncAfter` or a `Timer` (sticky-only-until-next-tap variant per UI-SPEC: no timer needed; the next chip tap clears via `setHighlighted(false)` on outgoing rows).

### Anti-Patterns to Avoid

- **Switching on `VerificationState` to assign a color anywhere other than `DS.Colors.Verification`.** D-04 grep gate forbids this. Any new code path that needs a color from a state MUST call `DS.Colors.Verification.color(for: state)`.
- **Walking `edges[].fromPartyID` to compute the attribution.** SPEC R9 forbids; the attribution comes from the role-hierarchy parent table, NOT from edge data. Edges are consulted ONLY by chain-integrity computation that drives the footer pill (R4).
- **Making tree rows tappable.** Out of scope per CONTEXT.md `<deferred>`; the row is `isUserInteractionEnabled = false`.
- **Dimming non-implicated tree rows, dashed-stroking flagged connectors, or pulsing implicated row outlines on iPhone.** SPEC R7 explicitly forbids; the footer pill carries the entire fraud signal on iPhone.
- **Mounting `ChainIntegrityBannerView` above the title bar on iPhone.** R4 explicitly removes this from iPhone scroll order.
- **Re-positioning Phase 9 `TrustGraphView` on iPad or modifying it in any way.** R10 explicitly preserves the iPad contract; any change re-opens Phase 9 spec.
- **Putting the role-hierarchy parent table in `Core/Load/Role.swift` (or any file under `Core/Load/`).** R11 forbids changes there; the table is a UI-layer convention.
- **Using SwiftUI for any 9.1 component.** CLAUDE.md mandates UIKit for marquee surfaces; the chain-of-vouches surface inherits from Phase 9's UIKit lock.
- **Adding `Logger`, `os_log`, or `print` calls to any 9.1 view file.** T-08-08 / T-09-04 view-layer logging lock; party `displayName` values are PII-class data.
- **Computing dashed-line geometry via a single tree-wide CAShapeLayer.** See §1 comparison table — couples row resize logic.

## Common Pitfalls

### Pitfall 1: Re-attaching CALayer animations and connector paths after `traitCollectionDidChange`

**What goes wrong:** Phase 9's `TrustGraphView` learned the hard way (Pitfall 1 / RESEARCH §2 line 967) that `CABasicAnimation` instances and `CAShapeLayer.path` values do not survive certain layout invalidations — the pulse animation has to be re-attached in BOTH `layoutSubviews()` AND `traitCollectionDidChange(_:)`. The 9.1 connector layers and highlight layers have the same lifecycle concern: a rotation or Dynamic Type flip can invalidate the path.

**Why it happens:** `CAShapeLayer.path` is a `CGPath?` — `setNeedsLayout` doesn't recompute it; `layoutSubviews()` must do so explicitly. Animation instances added with `isRemovedOnCompletion = false` survive layout but their target keypath value (`opacity`) reverts on certain transitions.

**How to avoid:** Recompute connector `path` in every `layoutSubviews()` call (Pattern 1 sketch shows this). Recompute highlight `path` in every `layoutSubviews()` call (Pattern 4 sketch shows this). For the chip-tap highlight animation, use `fillMode = .forwards` + `isRemovedOnCompletion = false` (Pattern 4 sketch).

**Warning signs:** Connector disappears after rotation. Highlight outline disappears after Dynamic Type change. Both are direct regressions of the Phase 9 Pitfall 1 lock.

### Pitfall 2: `convert(_:to:)` returns garbage if either view is not in the same window

**What goes wrong:** On the first layout pass (or during a composition rebuild), `convert(_:to:)` may be called before the tree row has been added to the window hierarchy — the result is undefined.

**Why it happens:** UIKit coordinate conversion walks the ancestor chain; if any ancestor's `window` is `nil`, the chain breaks at that point.

**How to avoid:** Guard with `firstRow.window != nil && outerScrollView.window != nil` before calling `convert`. Defer the scroll-to-row to the next runloop if the window isn't ready: `DispatchQueue.main.async { self.handleStripChipTap(role: role) }`.

**Warning signs:** Chip tap on first appearance scrolls to (0, 0) instead of the row. UI test for the chip-tap flow flakes intermittently.

### Pitfall 3: Stacking a horizontal sibling-row sub-stack inside the vertical tree stack

**What goes wrong:** Tempting to model "two brokers as siblings" as a horizontal `UIStackView` inside the vertical tree stack. This breaks (a) the scroll-anchor pattern (need to scroll to a horizontal pair, not a single row), (b) the highlight outline (one outline around the pair vs. two outlines around each row), and (c) the canonical accessibility order (UI-SPEC line 300 walks siblings by partyID alphabetical — order is per-row, not per-pair).

**Why it happens:** The visual reference photo shows two broker rows on the same horizontal baseline. But the spec says "siblings under the role-hierarchy parent" — siblings can be vertically stacked at adjacent indices, and the connector geometry (Pattern 1) draws the Y-fork. The visual baseline is the connector's fork bar, not the row baseline.

**How to avoid:** Each row is its own arrangedSubview in the single vertical tree stack. The connector layer's Y-fork handles the visual; the stack handles only sequencing.

**Warning signs:** Code starts using `if siblings.count > 1 { let hStack = ... }` — that's the wrong path. The right path keeps the stack uniformly vertical.

### Pitfall 4: Forgetting the CR-02 reparenting fix when extending size-class routing

**What goes wrong:** `LoadDetailViewController.buildIPadSplitLayout` moves `bodyView` into `rightPaneContainer`. On the iPad→iPhone return path, `buildIPhoneLayout` must reparent `bodyView` back into `bodyContainer` (the CR-02 fix at `LoadDetailViewController.swift:504-507`). The 9.1 changes ADD `everyoneOnLoadStripView`, `chainOfVouchesView`, and (on the DEBUG branch) `trustGraphView` — all of which must follow the same reparenting discipline if they ever move between containers.

**Why it happens:** AutoLayout cannot satisfy a constraint between two views in different subtrees. A trait flip that creates constraints between the new component and `bodyContainer` while the component is still a child of (say) `rightPaneContainer` produces runtime constraint-conflict logs and silently broken layout.

**How to avoid:** For 9.1 specifically, the new components ONLY mount on iPhone — they never move into the iPad split. So the planner can keep them as simple `bodyContainer` subviews and skip the reparenting dance. But if a future refactor moves them, mirror the CR-02 pattern.

**Warning signs:** "Unable to simultaneously satisfy constraints" in console on iPad→iPhone rotation.

### Pitfall 5: Phase 8 `Pitfall 8` — pill cornerRadius not recomputed in layoutSubviews

**What goes wrong:** A "pill" shape (full-rounded ends) needs `layer.cornerRadius = bounds.height / 2` in `layoutSubviews`. Hardcoding the corner radius to a literal point value works at default font size but turns into a square slab at large Dynamic Type sizes. The footer pill in 9.1 must follow this rule (UI-SPEC line 245).

**Why it happens:** `cornerRadius` is a `CGFloat` property, not a percentage — it doesn't track `bounds`.

**How to avoid:** Mirror `VerificationBadgeView.layoutSubviews()` at line 92-97: `super.layoutSubviews(); layer.cornerRadius = bounds.height / 2`.

**Warning signs:** Footer pill renders as a square at AX size categories.

### Pitfall 6: `adjustsImageSizeForAccessibilityContentSizeCategory` missed on the footer-pill SF Symbol

**What goes wrong:** SF Symbols configured with `UIImage.SymbolConfiguration(textStyle: .footnote)` track Dynamic Type for the BASE font sizes but NOT for the AX (accessibility) sizes unless `adjustsImageSizeForAccessibilityContentSizeCategory = true` is set on the `UIImageView`. At `.accessibilityExtraExtraExtraLarge`, the body text grows ~2.4x but the symbol stays at footnote size — illegible.

**Why it happens:** Apple's API split: base sizes are automatic, AX sizes require opt-in.

**How to avoid:** Set `adjustsImageSizeForAccessibilityContentSizeCategory = true` on every `UIImageView` rendering an SF Symbol with a textStyle configuration. Precedent at `ChainIntegrityBannerView.swift:82` (the CR-03 fix).

**Warning signs:** Snapshot test at `.accessibilityExtraExtraExtraLarge` shows tiny symbol next to large text.

### Pitfall 7: The role-hierarchy fallback when an intermediate role is missing

**What goes wrong:** UI-SPEC line 262 specifies fallback semantics: `.carrier` without a `.broker` attributes to `.shipper` ("VIA SHP"); `.dispatch` without a `.carrier` attributes to `.broker` ("VIA BRK"). A naive parent-table lookup `table[child]` returns `.broker` for a Carrier even when the chain has no Broker — leaving the Carrier visually orphaned (parent row doesn't exist).

**Why it happens:** The static parent table encodes the **canonical** hierarchy. The actual chain may be sparse (e.g., VL-1003 is shipper-only or shipper+carrier).

**How to avoid:** The attribution lookup walks UP the canonical hierarchy until a role present in the chain is found, OR returns nil for the topmost present role:

```swift
private static let canonicalParents: [Role: Role] = [
    .broker: .shipper, .carrier: .broker,
    .dispatch: .carrier, .factoring: .carrier,
]
private static func attributionParent(
    for role: Role,
    presentRoles: Set<Role>
) -> Role? {
    var current = role
    while let parent = canonicalParents[current] {
        if presentRoles.contains(parent) { return parent }
        current = parent
    }
    return nil  // root (Shipper, OR the topmost present role in a sparse chain)
}
```

**Warning signs:** A 2-node fixture (e.g., shipper + carrier with no broker) renders the carrier with "VIA BRK" attribution to a non-existent parent row, and the connector layer points at nothing.

### Pitfall 8: `traitOverrides` for snapshot tests must be applied BEFORE `configure()`

**What goes wrong:** Phase 9 hit this exact bug (WR-04, fixed at `TrustGraphViewSnapshotTests.swift:55-67`). If `traitOverrides.preferredContentSizeCategory = .accessibilityExtraExtraExtraLarge` is set AFTER `configure()` + `layoutIfNeeded()`, the view has already laid out at the default content size; the override has no visible effect (snapshot variants render identically).

**Why it happens:** The trait override modifies the trait collection on the view, but views only consult the trait at layout time. A view that has already completed layout doesn't re-consult.

**How to avoid:** Apply the override IMMEDIATELY after the bounds-set and BEFORE configure:

```swift
let v = ChainOfVouchesView()
v.bounds = CGRect(origin: .zero, size: size)
v.overrideUserInterfaceStyle = .light
v.traitOverrides.preferredContentSizeCategory = contentSize  // BEFORE configure
v.configure(chainOfTrust: chain)
v.layoutIfNeeded()
```

**Warning signs:** Snapshot variants at `.large` and `.accessibilityExtraExtraExtraLarge` produce visually identical attachments.

## Open Questions (RESOLVED)

### Q1. Strip-chip collapsed-state verification color rule

**What we know:** D-10 says tapping the BRK chip highlights ALL broker rows in the tree. UI-SPEC line 214 says the strip collapses VL-1009's two brokers to ONE chip. UI-SPEC line 222 says each chip's a11y label includes a `<VerificationStateCopy>`.

**What's unclear:** When two brokers have different verification states (one `.flagged`, one `.verified`), what state does the COLLAPSED chip show?

**Recommendation:** **Most-suspicious-wins** ordering (`.flagged > .pending > .unverified > .verified`). Rationale: the chameleon-broker fraud archetype is "one of the brokers is the bad actor" — surfacing the worst-of state at the chip level matches the platform thesis. The chip's a11y label then carries the most-suspicious state copy. The tree rows render their per-node states correctly.

Flag for planner: if user disagrees, the alternative is "show `.flagged` only when ALL nodes are flagged" (more conservative) or "show no chip-level state when the role has heterogeneous states" (most conservative). The most-suspicious rule is the natural fraud-first choice; planner should accept or escalate.

### Q2. NSLocalizedString key prefix collision

**What we know:** UI-SPEC line 168 declares the key prefix `loads.detail.chain.9_1.*`. Phase 9's `ChainIntegrityBannerView` uses `loads.detail.banner.*` (line 212-258 of that file).

**What's unclear:** Whether to keep both prefixes side-by-side (Phase 9 keys for iPad-mounted banner, Phase 9.1 keys for iPhone-mounted footer pill) or migrate the banner copy under the new prefix.

**Recommendation:** **Keep both prefixes.** Phase 9's banner is preserved on iPad (R10); its key set is the iPad authoritative copy. Phase 9.1's footer pill is a new visual element on iPhone with a different copy template (UI-SPEC lines 178-180: `"✓ Chain intact · %@"` etc.) — different keys, no collision.

### Q3. Fixture re-author scope (UI-SPEC line 187)

**What we know:** UI-SPEC suggests `chainIntegrity.reason` should read `"4 vouches, no anonymous parties"` for clean fixtures (VL-1001 / VL-1003 / VL-1005 / VL-1007) to support the affirmative footer pill cadence.

**What's unclear:** Whether this fixture re-author is in scope for 9.1 or deferred.

**Recommendation:** **In scope as a small additive task.** Fixture text-content changes are NOT data-model changes (R11 forbids the latter, not the former). The reason values live in JSON fixtures under `validationLedgerTests/Networking/Fixtures/load-detail-VL-*.json` (and possibly the Mock app's fixtures); a 4-fixture text edit is a low-risk leaf task. Confirmed by UI-SPEC line 187 ("This is a fixture text-content change, NOT a data-model change").

### Q4. `LaunchFlags` helper home

**What we know:** D-12 introduces `-Mock2DTrustGraphOnIPhone`. D-12 says it mirrors `MockDefaultFixtures.swift` precedent — but that file is about HTTP mock fixtures, not about app-wide debug flags.

**What's unclear:** Whether the new flag's helper logic (parse, expose `isActive`, expose `launchFlag` literal for tests) lives inline in `LoadDetailViewController` or in a new `LaunchFlags` (or `DebugFlags`) helper alongside `MockDefaultFixtures`.

**CRITICAL FINDING from §4:** This codebase's snapshot tests are **attachment-only** — `UIKitSnapshot.attach(image:name:to:)` writes a `UIImage` as an `XCTAttachment` for human review on CI; there are **no `.png` reference images on disk** and **no automated pixel-diff failure mode**. The implication for D-05:

1. **No baselines to "delete."** A grep of the test bundle for `.png` files returns zero results. There is nothing to remove.
2. **Re-recording = updating test method names + body to use iPad bounds.** The actual work is:
   - Edit `TrustGraphViewSnapshotTests.swift` to remove the iPhone-size test methods (`test_..._iPhonePortrait_...`) — D-05 says iPhone baselines deleted.
   - Edit the same file to add iPad mini portrait + landscape variants (`test_..._iPadMiniPortrait_...`, `test_..._iPadMiniLandscape_...`).
   - Same for `TrustNodeViewSnapshotTests.swift` and `ChainIntegrityBannerViewSnapshotTests.swift`.
3. **WR-04 collapse (D-06) is trivial in this model.** The "human reviewer walks the new iPad baselines once" is literally "open the test report in Xcode and inspect the attachments." No baseline file to diff.

**Recommended re-record steps for the planner:**

1. Run `git grep -E "iPhone.*Portrait|iPhone.*Landscape" validationLedgerTests/Loads/Snapshot/` to enumerate iPhone-sized snapshot test methods in the three files.
2. For each iPhone-sized method in `TrustGraphViewSnapshotTests.swift` / `TrustNodeViewSnapshotTests.swift` / `ChainIntegrityBannerViewSnapshotTests.swift`: REMOVE the method (D-05 deletes iPhone baselines), or RENAME its size constant to `iPadMiniPortraitSize` / `iPadMiniLandscapeSize`.
3. Add new iPad-sized methods if a verdict × Dynamic Type combination needs iPad coverage that wasn't there before.
4. Run the suite on the iPad mini simulator; the attachments populate the CI artifact bundle.
5. Human review (D-06) is inspection of the new attachments via Xcode test report.

This is significantly less work than "delete baselines + re-record" implies in a pixel-diff snapshot framework. **The planner should size the D-05 task accordingly** — it's a 1-task edit, not a 4-task workflow.
