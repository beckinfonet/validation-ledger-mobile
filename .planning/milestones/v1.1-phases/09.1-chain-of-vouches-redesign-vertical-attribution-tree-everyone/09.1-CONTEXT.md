# Phase 09.1: Chain-of-Vouches Redesign — vertical attribution tree + everyone-on-load strip - Context

**Gathered:** 2026-05-20
**Status:** Ready for planning

<domain>
## Phase Boundary

On iPhone, the chain-of-trust visualization changes from the Phase 9 2D positioned-node `TrustGraphView` (824 LOC, scope of the device-UAT defects 2026-05-20) to two new top-anchored components:

- **`EveryoneOnLoadStripView`** — a horizontally-scrollable dynamic strip of role-avatar chips; only roles actually present in the chain appear (2 to 5 chips across the 9-fixture corpus).
- **`ChainOfVouchesView`** — a vertical attribution tree card with per-row avatar + role name + "VIA X" attribution + display name, dashed connectors, a Y-fork for the CAR → {DSP, FCT} sibling case, and the chain-integrity verdict folded into a footer pill inside the card (the Phase 9 standalone `ChainIntegrityBannerView` is no longer mounted above the iPhone title bar — its component file is preserved but only mounts on iPad).

Both consume a new `RoleAvatarView` primitive (programmatic UIView with per-role colored circle + 3-letter abbreviation + bottom-right verification-state dot).

On iPad regular-width, Phase 9 `TrustGraphView` is preserved unchanged: identical view hierarchy, identical 32 trust-graph tests stay green, identical D-15 dim-others / dashed-flagged-edges visual language. The new components are siblings, not replacements.

The `ChainOfTrust` data model (`Core/Load/ChainOfTrust.swift` + neighbors) is FROZEN for 9.1 (SPEC R11). Every new view consumes existing fields. The "VIA X" attribution uses a fixed role-hierarchy table (BRK → SHP, CAR → BRK, DSP → CAR, FCT → CAR), not the `edges[].fromPartyID` data — multi-broker chains (VL-1009) render both brokers as siblings under SHP regardless of edges; the chain-integrity footer pill carries the entire fraud-signaling burden via verdict copy + tint.

What this phase is **NOT**:
- Any iPad layout changes — Phase 9's iPad composition is the contract (SPEC R5, R10).
- Any `ChainOfTrust`/`TrustNode`/`TrustEdge`/`ChainIntegrity`/`PriorRelationship` data-model changes (SPEC R11).
- Presence indicators / "All watching live" realtime substrate — the strip carries the static caption text only; no realtime wiring (M3).
- Animation/transition polish between the strip and the tree beyond a brief highlight on chip tap (UI-SPEC owns specifics; deferred from scope guidance).
- Push notifications for chain-integrity changes (M3).
- Edge-data-driven "VIA X" attribution (explicitly superseded by role-hierarchy attribution, SPEC R9).
- Changes to the `VerificationState` enum upstream — the enum stays; only the color-ramp implementation moves (SPEC R12).

## Implementation Decisions

### Shared verification color helper (SPEC R12)

- **D-01:** The shared verification color helper lives **inside `DS.Colors` as a nested `Verification` namespace** in `validationLedger/UI/DesignSystem/Colors.swift`. The Phase 9 `DS.Colors.caution` token already lives in this file; keeping the verification ramp colocated keeps "all design-system tokens in one file" the rule. Exact signature is planner discretion (most natural: a single `static func color(for: VerificationState) -> UIColor` returning the dot/background color, since that's the ONLY color the dot needs and the only color shared between the badge and the avatar).
- **D-02:** `VerificationBadgeView` is refactored to call `DS.Colors.Verification.color(for: state)` for its `backgroundColor`. The badge keeps its inline ownership of the SF Symbol icon, the label copy, the icon tint, the label text color (`.white` / `.label` / `.secondaryLabel`), and every `accessibilityLabel` string — those are NOT shared with `RoleAvatarView`. The badge's existing TRUST-02 lock comment at the top of `VerificationBadgeView.swift` is relocated or duplicated as a comment block at the top of the new `Verification` namespace declaration in `Colors.swift`, so the single-source-of-truth invariant is documented where the colors actually live.
- **D-03:** `RoleAvatarView`'s status-dot color reads from `DS.Colors.Verification.color(for: verificationState)` — same call site, same source of truth. The dot maps all 4 states (verified / pending / unverified / flagged) per the SPEC R1 acceptance test (5 roles × 4 verification states = 20 cases asserted against the shared helper's output).
- **D-04:** The R12 negative-grep gate asserts `VerificationState`→`UIColor` mapping appears in exactly one source file. The grep pattern targets the `switch state` over `VerificationState` cases mapping to color assignments (e.g. `case .verified: return DS.Colors.primary`). Both `VerificationBadgeView.apply(state:)` and the future `RoleAvatarView` configuration code MUST call the helper — neither may switch on state to assign a color directly.

### Phase 9 trust-graph snapshot test posture (SPEC R5, R10)

- **D-05:** The Phase 9 trust-graph snapshot tests are **constrained to iPad regular-width frames only**. Existing iPhone baselines under `validationLedgerTests/Loads/Snapshot/` for `TrustGraphView`, `TrustNodeView`, and `ChainIntegrityBannerView` are **deleted**, and the tests are re-recorded at iPad sizes (iPad mini portrait + landscape are the indicative targets; planner finalizes the exact size set in coordination with `UIKitSnapshot.swift`'s helpers). Rationale: iPhone no longer mounts those views per R5; keeping iPhone baselines tests a code path the app never actually presents.
- **D-06:** The pre-existing WR-04 baseline sanity-check follow-up from the Phase 9 close-out (project memory `phase-9-execution-closeout`) **resolves in the same re-record pass** — when the planner deletes iPhone baselines and re-records at iPad sizes, the human sanity-check on WR-04 collapses into reviewing the new baselines. No separate WR-04 pass is needed.
- **D-07:** The 32 Phase 9 trust-graph unit/gesture/accessibility tests (`TrustGraphView{Layout,Accessibility,Gesture}Tests.swift`, `TrustNodeViewGestureTests.swift`, etc.) continue to run **without size-class restriction** — they exercise the view layer directly, not the size-class routing, so they don't need to flip. Only the *snapshot* baselines change. SPEC R10 acceptance ("all 32 Phase 9 trust-graph tests continue to pass on iPad simulator") is preserved.

### "Everyone on this load" strip interactivity (backlog open Q5)

- **D-08:** Chips in `EveryoneOnLoadStripView` are **interactive**: a tap on a chip scrolls `ChainOfVouchesView` to that role's row(s) and applies a brief highlight. Each chip gets the `.button` accessibility trait (in addition to the composed role + display-name + verification-state a11y label from SPEC R6). The reference photo's "selected chip with darker tinted background panel" is supported via this same selection state.
- **D-09:** Selection state is keyed by **`Role`** (not `partyID`). This is the architecturally correct choice given SPEC R2's collapse rule (VL-1009's two brokers render as one chip in the strip). The strip exposes either an `onRoleTap: (Role) -> Void` closure or a `delegate` (planner discretion — the precedent across Phase 8 collection-view cells is closures), wired by `LoadDetailViewController` (or a small new owner) to call `ChainOfVouchesView.applySelectedRole(_ role: Role?)`.
- **D-10:** For multi-role chains (currently only VL-1009 with two brokers), tapping the collapsed BRK chip highlights **ALL rows for that role** — both FreightWise and Keystone broker rows get the highlight outline; the tree scrolls so the top of the broker sibling group is visible (so both rows are on-screen). Matches the platform thesis: "the role is suspect, not just one party" — relevant for the chameleon-broker fraud archetype VL-1009 dramatizes.
- **D-11:** The highlight visual (color/token, stroke width, animation duration, fade-in / fade-out timing, whether the highlight is sticky until another chip is tapped or auto-dismisses after N seconds) is UI-SPEC 9.1 concern. The reference photo shows a green outline matching the verified-state color; the natural choice is `DS.Colors.primary` (already `.systemBlue`, brand "verified" color) or a verified-state pull from the new `DS.Colors.Verification` namespace. UI-SPEC owns final tokens.

### DEBUG-only iPhone 2D-graph fallback (backlog open Q1)

- **D-12:** A DEBUG-only launch argument **`-Mock2DTrustGraphOnIPhone`** is added, mirroring the `-MockKYCStatusVerified` precedent established 2026-05-20 (`validationLedger/Core/Networking/Mock/MockDefaultFixtures.swift` lines 32, 69, 71). When present, the iPhone code path in `LoadDetailViewController.buildIPhoneLayout` instantiates Phase 9 `TrustGraphView` instead of the new `EveryoneOnLoadStripView` + `ChainOfVouchesView`. iPad behavior is unchanged regardless of the flag.
- **D-13:** The flag is **`#if DEBUG`-gated**; the iPhone-graph branch and the `ProcessInfo.arguments.contains(...)` check are stripped from Release builds. No production code path can hit the 2D iPhone layout. The grep gate from D-04 is unaffected (the 2D path still calls the shared color helper).
- **D-14:** Use case: marketing screenshots, App Store screenshots, press shots — the 2D graph with the pulse-on-compromised glow is visually striking even though it's unreadable for actual chain-reading at iPhone widths. The flag preserves that artifact without dragging dead code into production. A small unit test asserts the flag is honored when set; a comment block in `LoadDetailViewController` documents the toggle alongside the existing `-MockKYCStatusVerified` precedent reference.

### Claude's Discretion

The planner / researcher / UI-researcher may finalize without re-asking the user:

- **File partitioning for `ChainOfVouchesView`** — single `ChainOfVouchesView.swift` containing the tree + row + Y-fork + footer-pill subviews inline, vs. a `ChainOfVouches/` subdirectory with `ChainOfVouchesView.swift` + `ChainOfVouchesRowView.swift` + `ChainOfVouchesConnectorView.swift` + `ChainIntegrityFooterPillView.swift`. Either is acceptable; the precedent across `Features/Loads/Detail/` is one file per primary view but the directory is already at 12 files, so a subdirectory split is reasonable when row + connector code crosses ~150 LOC.
- **Role-hierarchy parent table location** (the `BRK → SHP, CAR → BRK, DSP → CAR, FCT → CAR` lookup from SPEC R9). Natural home: a `private static let` map on `ChainOfVouchesView` or its tree-builder helper. An alternative is an extension on `Role` (e.g. `Role.attributionParent` returning `Role?`); since `Role` lives in `Core/Load/` and the parent table is purely a UI-layer convention (not a domain truth), the UI-side helper is the cleaner placement.
- **The strip's "All watching live" caption exact wording and placement** (right-edge meta caption per SPEC R2). The reference photo shows "All watching live · tap for details". UI-SPEC 9.1 locks the exact NSLocalizedString key + comment + final caption text.
- **The card's title + caption + subtitle exact wording.** The reference shows "Chain of vouches" / "Every party attested" / "Every party on this load is here because someone above them attested to them. Tap a chip to see the vouch." UI-SPEC 9.1 owns final localized strings.
- **The footer pill copy template** for clean / flagged / compromised verdicts. Reference shows "✓ Chain intact · 4 vouches, no anonymous parties" for clean. The "no anonymous parties" cadence may require a fixture re-author pass on `ChainIntegrity.reason` (NOT a data-model change; the field is already populated by fixtures). UI-SPEC owns the template; if fixture re-authoring is needed, it's a small additive task in the plan, not a data-layer change.
- **Per-role brand colors** for the avatar circles (the reference photo shows blue/orange/green/purple/blue for SHP/BRK/CAR/DSP/FCT). UI-SPEC owns the exact palette; tokens land in `DS.Colors` under a new `Roles` namespace (parallel to the new `Verification` namespace from D-01) or inline on `RoleAvatarView`.
- **The exact strip-tap highlight visual** (D-11) — outline color token, stroke width, animation duration. UI-SPEC.
- **The exact card visual** (corner radius, padding, background fill, shadow/border) — UI-SPEC owns; consumes existing `DS.Spacing` / `DS.Colors` tokens.
- **Scroll-anchor point** when a chip tap scrolls the tree — top-of-row vs. center-of-row vs. "make the entire sibling group visible." Planner discretion; for VL-1009 the planner should pick the variant that puts both broker rows on-screen.
- **iPad TrustGraphView size-class routing implementation** — whether `LoadDetailViewController.traitCollection.horizontalSizeClass` is read in `buildIPhoneLayout` directly, or via a `traitCollectionDidChange(_:)` override, or via a `UITraitMutations` (iOS 17+) registration. Pick the precedent that fits cleanest with the Phase 9 CR-02 reparenting fix.
- **Unit test scaffolding location** for the new components — under `validationLedgerTests/Loads/` matching the Phase 9 layout, or a new `validationLedgerTests/Loads/Detail/` subdirectory. Planner discretion.
- **Snapshot test size set** for the new components (iPhone 15 portrait + iPhone SE landscape at minimum; iPhone 17 Pro Max optional). Match the Phase 9 snapshot test conventions in `validationLedgerTests/Support/UIKitSnapshot.swift`.

## Specific Ideas

- **The reference photo IS the design contract.** The backlog file (`.planning/backlog/09.1-chain-of-vouches-redesign.md`) transcribes the photo into prose. The two surfaces (strip on top, vertical tree below) and their structural elements (avatar + 3-letter abbrev + bottom-right dot for the strip chips; row pill with avatar + role name + "VIA X" + display name for the tree; dashed Y-fork connectors; green footer pill for integrity) are exactly what the user reviewed during device UAT 2026-05-20 and committed to via the "Big" option. UI-SPEC 9.1 should lift the reference's exact copy verbatim where possible (`"Everyone on this load"`, `"All watching live · tap for details"`, `"Chain of vouches"`, `"Every party attested"`, the subtitle text, the `"✓ Chain intact"` cadence).

- **"The role is suspect, not just one party"** is the multi-broker fraud-signaling intent (D-10). When the strip collapses VL-1009's two brokers into one BRK chip, and the user taps that chip, BOTH broker rows in the tree light up — because the chameleon-broker re-tender fraud archetype is about the role being abused, not about either FreightWise or Keystone individually being the bad actor. The tree-row highlight visual should be the same on both rows (no "primary vs. secondary" treatment) so the spatial reading is "two brokers, same role, both vouched the same way (VIA SHP), both implicated."

- **TRUST-02 was a Phase 8 lock that 9.1 strengthens, not weakens.** The color ramp moving out of `VerificationBadgeView` into `DS.Colors.Verification` (D-01) means BOTH the badge AND the new avatar dot are forced to call the same function — a stronger structural guarantee than "we wrote a comment about TRUST-02 in one file and remembered not to add a second copy." The negative-grep gate (D-04) makes the lock enforceable by tooling, not just discipline.

- **The DEBUG-only 2D-graph flag is a marketing surface, not a developer convenience.** D-12 is not about giving engineers a way to "compare the old and new designs at runtime" — it's about preserving the visually striking pulse-on-compromised marquee animation for App Store screenshots and press shots, in a tightly-gated path that never reaches a Release binary. If the planner sees this as a developer feature, they should re-read this section: the gate should be aggressive enough that you'd have to actively flag it in scheme arguments, not happen to enable it.

- **Phase 9 is the iPad contract; 9.1 is the iPhone redesign that doesn't disturb the contract.** Every iPhone change in 9.1 ends at the size-class boundary. iPad sees nothing different — same TrustGraphView, same 32 tests, same banner above the title bar, same D-15 visual language. The planner should treat any temptation to "simplify by removing the iPad path too" as a NON-STARTER (it's an explicit R10 violation and would re-open the entire Phase 9 spec).
