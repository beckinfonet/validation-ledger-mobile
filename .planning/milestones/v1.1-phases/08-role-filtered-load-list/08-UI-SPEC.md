# Phase 8 — UI Design Contract

> Visual and interaction contract for the **Role-Filtered Load List** phase. Generated by gsd-ui-researcher; verified downstream by gsd-ui-checker.
>
> **Platform note:** This is a native iOS UIKit client (iPhone + iPad, iOS 17+), not a web project. The shadcn initialization gate and component-registry safety gate are **not applicable** — there is no `components.json`, no Tailwind, no React. The "Design System" section describes the existing in-repo UIKit token layer (`validationLedger/UI/DesignSystem/`).
>
> **Phase 8 frame** (orchestrator-supplied): the first v1.1 surface that renders freight data. It delivers each role's "Loads" tab (Broker, Shipper, Carrier, Dispatch, Factoring), the standard freight row, the reusable verification badge component (4 states), distinct empty/loading/error states, and pull-to-refresh. The list is filtered fixture-side per role (LOAD-03) — the client never re-filters. Phase 7's `Core/Load/` domain kernel + 3 typed endpoints + fixture matrix are the contract this UI reads.

## UIKit vs SwiftUI Decision (locked)

**Decision: UIKit, programmatic, no XIB / Storyboard.**

CLAUDE.md permits SwiftUI only for "non-critical surfaces like Settings/static lists." The load list is **not** a non-critical surface — it is the first freight-data surface, the one users will touch most, the source of every Phase 9 navigation, and the home of the reusable verification badge that Phases 9–11 will reuse on chain-of-trust graph nodes (TRUST-02). Mixing SwiftUI here would (a) split the codebase's UIKit-fluency baseline before the chain-of-trust graph (Phase 9, locked UIKit), (b) introduce a SwiftUI ↔ UIKit interop seam at the navigation push into the Phase 9 detail screen, and (c) force the verification badge to be written twice. Every shipped v1.0 surface — KYC capture/review/status, OTP/phone-entry, role tab bars, Profile modal — is UIKit. Phase 8 continues the precedent.

- View controllers: subclasses of `UIViewController` registered with the existing `RoleCoordinator` and `wrapTabsWithNavAndInstallAvatar` machinery — no new container patterns.
- List rendering: `UICollectionView` with a `UICollectionViewCompositionalLayout(.list)` + `UICollectionViewDiffableDataSource`. Chosen over `UITableView` for clean iPad regular-width readable-content-guide behavior and modern diffable updates from the pull-to-refresh path. (`UITableView` would also work; the executor must use **exactly one** of the two — no mix.)
- Pull-to-refresh: `UIRefreshControl` attached to the collection view (matches the precedent in `KYCStatusViewController`).
- Cells: a single `UICollectionViewListCell` subclass for the freight row. Auto-layout, programmatic, `adjustsFontForContentSizeCategory = true` on every label.

## Reusable Component Inventory

Phase 8 introduces **two** new view-layer types intended for reuse in Phases 9–11. Both live under `validationLedger/UI/Components/` (new directory) — NOT under `Features/Loads/` — because TRUST-02 explicitly requires the badge to be shared with the load detail and chain-of-trust graph.

| Component | File | Reused by | Behavior |
|-----------|------|-----------|----------|
| `VerificationBadgeView: UIView` | `UI/Components/VerificationBadgeView.swift` | Phase 8 load row, Phase 9 detail header, Phase 9 chain-of-trust graph nodes, Phase 10 disabled-tender inline reason | Renders one of 4 `VerificationState` cases (verified / pending / unverified / flagged) as a pill: SF Symbol + uppercase label + colored fill. Size matches a single line of `.caption1` (footnote-adjacent); minimum hit area not required (badge is not interactive — Phase 9 makes the graph-node container tappable, not the badge itself). |
| `LoadStatusBadgeView: UIView` | `UI/Components/LoadStatusBadgeView.swift` | Phase 8 load row, Phase 9 detail header, Phase 9 timeline current-state marker | Renders one of 13 `LoadStatus` cases as a pill: uppercase label + neutral fill. NOT a security primitive — the color ramp is informational, NOT the verification ramp. See § Color → "Status badge color rules" below. |

Both components are pure `UIView` subclasses with a single `func configure(state: VerificationState)` (or `status: LoadStatus`) entry point. No `Combine`, no `@State`, no async work — pure render-from-input.

**LoadRowCell** (`Features/Loads/Cells/LoadRowCell.swift`) composes both badges. It is **not** itself a reusable component — it is the Phase 8 cell.

## Spacing Scale

Declared values — the existing `DS.Spacing` enum (`validationLedger/UI/DesignSystem/Spacing.swift`), all multiples of 4:

| Token | `DS.Spacing` member | Value | Usage in Phase 8 |
|-------|---------------------|-------|------------------|
| xs | `DS.Spacing.xs` | 4pt | Icon-to-label gap inside `VerificationBadgeView` and `LoadStatusBadgeView`; gap between origin city/state and the `→` arrow |
| sm | `DS.Spacing.sm` | 8pt | Vertical gap between rows of metadata inside a load cell (e.g. between origin→destination line and pickup/delivery dates); badge-internal vertical inset |
| md | `DS.Spacing.md` | 16pt | Default cell content padding (leading/trailing/top/bottom inside the row); spacing between the two badge cluster and the rest of the row; default collection-view section inset |
| lg | `DS.Spacing.lg` | 24pt | Screen leading/trailing safe-area inset on iPhone compact (matches Auth + Phase 5); empty/error-state symbol-to-heading gap |
| xl | `DS.Spacing.xl` | 32pt | Empty/error-state heading-to-body gap; spacing above an empty-state secondary CTA (when present) |
| xxl | `DS.Spacing.xxl` | 48pt | Top inset for the centered empty / error state from the navigation bar bottom |

**Exceptions:**
- **44pt minimum touch target** — pull-to-refresh affordance hit area, every row's tap target (whole row), and every CTA on the error / empty state must each present a hit area ≥ 44×44pt (Apple HIG). 44 is not a `DS.Spacing` token; it is an explicit touch-target floor. The cell's `automaticDimension` row height naturally satisfies this for any non-empty row; the executor must add explicit `heightAnchor.constraint(greaterThanOrEqualToConstant: 44)` only on the empty/error-state action buttons.
- **Badge internal geometry** — `VerificationBadgeView` and `LoadStatusBadgeView` use `DS.Spacing.xs` (4pt) for horizontal label padding and `DS.Spacing.xs` (4pt) for vertical padding around the label, giving a pill height of roughly 20pt at the default Dynamic Type setting. Corner radius is `bounds.height / 2` (full pill). These two values (4pt × 4pt) are on the 4pt grid; no sub-grid spacing is introduced.
- **List separator inset** — `UICollectionLayoutListConfiguration.separatorConfiguration` uses `.systemBackground` color and a leading inset of `DS.Spacing.md` (16pt) — matches the standard iOS list look and stays on grid.

## Typography

Phase 8 uses the existing `DS.Typography` tokens, all backed by `UIFont.preferredFont(forTextStyle:)` so Dynamic Type and dark mode are automatic. Every label MUST set `adjustsFontForContentSizeCategory = true`. The table below pins the **four roles Phase 8 declares** and the system metrics at the default (Large) content size.

| Role | `DS.Typography` token | Text style | Size (default) | Weight | Line height (default) | Used for |
|------|----------------------|------------|----------------|--------|------------------------|----------|
| Display | `DS.Typography.title1` | `.title1` | 28pt | regular (400) | ~34pt (≈1.21) | Empty state heading ("No loads yet") and error-state heading ("We couldn't load loads"). Centered. |
| Heading | `DS.Typography.headline` | `.headline` | 17pt | semibold (600) | ~22pt (≈1.29) | The reference number on each load row (e.g. "REF-100A"); the empty/error-state action button title text; the navigation-bar title "Loads" |
| Body | `DS.Typography.body` | `.body` | 17pt | regular (400) | ~22pt (≈1.29) | Origin → destination line; rate line ($USD formatted); empty-state body copy; error-state body copy |
| Caption | `DS.Typography.footnote` | `.footnote` | 13pt | regular (400) | ~18pt (≈1.38) | Pickup/delivery dates (relative — "Pickup Tue 9 AM"); equipment + weight metadata; both badge labels; pull-to-refresh "Updated just now" text (if surfaced) |

**Weights:** exactly two — **regular (400)** for body/display/caption and **semibold (600)** for headings/reference numbers/button titles. This is what the iOS `.headline` vs `.body`/`.title1`/`.footnote` styles already give for free. No manual `.withWeight(...)` overrides, no bold/light/medium.

**Sizes:** exactly four roles declared (28 / 17 / 17 / 13). Body and Heading share the 17pt point size but differ by weight (regular vs semibold) — the standard iOS pairing and counts as the two distinct *roles* the contract requires. Do not introduce `.largeTitle`, `.title2`, `.callout`, or `.caption1` from the token file for Phase 8 screens.

**Reference number rendering note:** the reference number is the strongest hierarchical anchor on the row. It uses `.headline` (17pt semibold). The origin→destination uses `.body` (17pt regular). This is the **only** size/weight pairing in the row — every other metadata field uses `.footnote` (13pt regular) to keep the cell visually three-tiered (anchor / sub-anchor / metadata) rather than a flat block of equal-weight lines.

## Color

Phase 8 uses the existing `DS.Colors` tokens (`validationLedger/UI/DesignSystem/Colors.swift`), all mapped to iOS system semantic colors so dark mode and contrast are automatic. The 60/30/10 split below describes the load-list screen specifically.

| Role | Token / system color | Usage |
|------|----------------------|-------|
| Dominant (60%) | `DS.Colors.background` (`.systemBackground`) | Full-screen background of the load list, of every empty/loading/error state, and the cell content background |
| Secondary (30%) | `DS.Colors.surface` (`.secondarySystemBackground`) | Section header backgrounds (if used; Phase 8 currently uses a single un-headered section); skeleton-placeholder shimmer base (loading state); the `LoadStatusBadgeView` neutral fill |
| Accent (10%) | `DS.Colors.primary` (`.systemBlue`) | Reserved exclusively for the elements listed below |
| Destructive | `DS.Colors.destructive` (`.systemRed`) | Error-state heading text; the "flagged" verification badge fill (TRUST-02 semantic mapping); inline error icon on the error state |

**Accent (`systemBlue`) reserved for:**
1. The "Try again" CTA button on the **error state** (`UIButton.Configuration.borderedProminent()` — its tint is `systemBlue`).
2. The pull-to-refresh `UIRefreshControl` spinner tint.
3. The navigation-bar tint (system default).
4. The "verified" verification-badge fill (TRUST-02 semantic mapping).

Accent is **not** applied to body text, separators, the cell background, status badge fill, or any other non-interactive element.

### Verification badge color rules (TRUST-02 — locked)

The 4 `VerificationState` cases map to a closed, semantically meaningful color ramp. **This ramp is a security primitive** — VerificationState fails closed (`Core/Load/VerificationState.swift`), and the badge must visually fail just as closed: unknown → unverified → neutral-grey, never green.

| `VerificationState` | Fill color | Foreground / icon color | SF Symbol | Label |
|---------------------|------------|-------------------------|-----------|-------|
| `.verified` | `DS.Colors.primary` (`.systemBlue`) | `.white` | `checkmark.seal.fill` | "VERIFIED" |
| `.pending` | `.systemYellow` (no token — uses the existing `LimitedTrustBannerView` "caution" semantic) | `.label` | `clock.fill` | "PENDING" |
| `.unverified` | `.tertiarySystemFill` (neutral grey, system-managed for dark-mode contrast) | `.secondaryLabel` | `questionmark.circle.fill` | "UNVERIFIED" |
| `.flagged` | `DS.Colors.destructive` (`.systemRed`) | `.white` | `exclamationmark.triangle.fill` | "FLAGGED" |

The badge is on the 10% accent budget **only** for the `.verified` and `.flagged` rows — those reuse the existing `systemBlue` and `systemRed` semantics. `.pending` (yellow) and `.unverified` (neutral grey) are semantic capture-feedback colors paralleling the Phase 5 framing-guide colors — each has a distinct semantic meaning (caution / unknown) and is not on the brand-accent budget, exactly like the `LimitedTrustBannerView`'s `systemYellow` and Phase 5's `systemGreen` capture-ready color.

**The 4 colors are the only 4 the badge ever renders.** Adding a 5th case requires changing the `VerificationState` enum upstream, which would fail decode at the Phase 7 contract layer.

### Status badge color rules (informational — NOT a security primitive)

The 13 `LoadStatus` cases collapse into a 3-tone informational ramp. The status badge does NOT reuse the verification ramp — sharing color across two unrelated meanings would be a design bug.

| LoadStatus group | Cases | Fill | Foreground |
|------------------|-------|------|------------|
| In-progress (active) | `posted`, `tendered`, `accepted`, `dispatched`, `inTransit` | `.tertiarySystemFill` (neutral grey) | `.label` |
| Done | `delivered`, `podCaptured`, `invoiced`, `funded` | `.systemGray5` (slightly muted) | `.secondaryLabel` |
| Terminal-error | `rejected`, `expired`, `cancelled` | `.systemGray5` with a strikethrough on the label | `.secondaryLabel` |
| Pre-life | `draft` | `.systemGray6` (most muted) | `.secondaryLabel` |

The status badge text is **uppercase** (e.g. "IN TRANSIT") to read as a tag, not as body copy.

### Other non-blue/non-red colors

Two additional system colors appear and are explicitly justified:
- `.systemYellow` on the `.pending` verification badge — caution semantic, paralleling `LimitedTrustBannerView`.
- `.tertiarySystemFill` / `.systemGray5` / `.systemGray6` on status badges and the `.unverified` badge — these are *neutrals*, not chromatic colors; they signal "no chromatic semantic claimed."

No other colors are permitted in Phase 8 screens.

## Copywriting Contract

All strings are wrapped in `NSLocalizedString(_, value:)` with English fallbacks (matches the `LimitedTrustBannerView` + Phase 5 pattern — M1 ships English only, `Resources/en.lproj/Localizable.strings` is structured for v2). The orchestrator notes the standard freight field set in LOAD-04 — the copy below assumes that field set is rendered structurally (not narratively).

| Element | Copy |
|---------|------|
| Navigation title (all 5 roles) | **"Loads"** (matches the tab title already used in each role tab bar controller; never role-prefixed — the tab bar already encodes the role, so prefixing the title would be redundant and would leak role identity into the screen chrome) |
| Empty state heading | **"No loads yet"** |
| Empty state body — Broker / Shipper | *"Loads you post will appear here. There's nothing on your board right now."* |
| Empty state body — Carrier / Dispatch | *"Loads tendered to you will appear here. Nothing's been tendered yet."* |
| Empty state body — Factoring | *"Loads tied to your factoring relationships will appear here. Nothing's been invoiced yet."* |
| Empty state — no CTA | The empty state is informational only — there is no "Create a load" button in v1.1 (the multi-field load-creation form is deferred to `LOAD-F1`). The empty state shows the heading + body and nothing else. |
| Loading state heading | (none — the loading state is silent: a skeleton or `UIActivityIndicatorView`. No headline copy.) |
| Loading state — accessibility label | **"Loading loads"** (`UIAccessibility.post(notification: .layoutChanged, ...)` announces this on appearance for VoiceOver) |
| Error state heading | **"We couldn't load loads"** |
| Error state body | *"Check your connection and try again. Your loads are safe."* (the second sentence reassures — the user has no local mutation to lose, and the platform thesis ("identity that cannot be spoofed") shouldn't be undermined by a transient network blip implying data loss) |
| Error state primary CTA | **"Try again"** (re-fires the fetch; the same code path the pull-to-refresh uses) |
| Pull-to-refresh — no copy | `UIRefreshControl` shows the system spinner only — no "Pull to refresh" / "Release to refresh" attributed-title customization. Matches `KYCStatusViewController`. |
| Cell content — origin → destination | Format: **"{City}, {ST} → {City}, {ST}"** — e.g. *"Dallas, TX → Atlanta, GA"*. The arrow is a literal `→` (U+2192), with `DS.Spacing.xs` (4pt) padding on each side. |
| Cell content — pickup/delivery dates | Format: **"Pickup {RelDay} • Deliver {RelDay}"** where `{RelDay}` is `Date.RelativeDateTimeFormatter` for dates within 7 days (e.g. "Tue 9 AM"), and the explicit short-date form (e.g. "Jun 12") for dates further out. The bullet is `•` (U+2022). |
| Cell content — equipment + weight | Format: **"{Equipment} • {Weight} lb"** — e.g. *"Dry van • 42,000 lb"*. Equipment string is server-supplied freeform (LOAD-02 D-?, `Load.equipment`) — render exactly what the server emits, no client-side title-casing of unknown values. |
| Cell content — rate | Format: **"${Rate}"** with `NumberFormatter` `.currency` style, locale `en_US`. No cents on the cell (the row's tertiary metadata); the detail screen (Phase 9) can show cents if needed. |
| Cell content — verification-badge label | uppercase: **"VERIFIED" / "PENDING" / "UNVERIFIED" / "FLAGGED"** (matches § Color table above) |
| Cell content — status-badge label | uppercase, with `LoadStatus` cases mapped: **"DRAFT" / "POSTED" / "TENDERED" / "ACCEPTED" / "DISPATCHED" / "IN TRANSIT" / "DELIVERED" / "REJECTED" / "EXPIRED" / "CANCELLED" / "POD CAPTURED" / "INVOICED" / "FUNDED"** |
| Destructive confirmation | **None.** Phase 8 is read-only — no action buttons, no destructive paths. Destructive actions (tender to unverified, cancel) land in Phase 10 and will get their own UI-SPEC entries. |

**Counterparty disambiguation note for the planner:** the load row shows ONE verification badge — the badge for the *counterparty relevant to the signed-in role*. For a Broker viewing the list, this is the carrier; for a Carrier/Dispatch, the broker; for a Shipper, the broker; for a Factoring user, the carrier. The fixture is server-supplied so this resolution is server-side — the iOS row reads whichever counterparty's `TrustNode.verificationState` the server places at the top of the row's projection. (Open question for the planner: is there a `Load`-level `displayedCounterparty: TrustNode` field, or does the row VC pick from `ChainOfTrust.nodes` using `RoleLoadPolicy`? This is a contract clarification that may need to surface in Phase 8's research/plan step; the UI-SPEC fixes only the *rendering*, not the *selection*.)

## State Machine

The load-list screen has exactly four mutually exclusive top-level states. The view model exposes a single `@Published` (or async-stream) state enum that drives which sub-view is visible. No two states render simultaneously.

| State | Trigger | What renders | Test fixture (Phase 7) |
|-------|---------|--------------|------------------------|
| `.loading` | First appearance OR pull-to-refresh while no cached data is shown | `UIActivityIndicatorView` centered, or a skeleton collection view (executor's choice — both are acceptable). The collection view's actual cells are hidden. | The injected-latency fixture from Phase 7 D-14 |
| `.empty` | Successful fetch, `loads.isEmpty == true` | `UIContentUnavailableView` with the role-specific empty-state heading + body from § Copywriting. No CTA. | Per-role `loads-list-{role}-empty.json` from Phase 7 D-14 |
| `.loaded(loads)` | Successful fetch, `loads.isNotEmpty` | The collection view with one `LoadRowCell` per `Load`. Pull-to-refresh is available. | Each role's standard fixture from Phase 7 D-11 (the shared-world named-load library) |
| `.error(message)` | Network error, decode error, server error | `UIContentUnavailableView` with the error heading + body + "Try again" CTA from § Copywriting. Pull-to-refresh is also available as a redundant path. | The server-error fixture from Phase 7 D-14 |

The `.loading` → `.loaded` / `.empty` / `.error` transitions render abruptly (no animation), matching the Phase 4/6 ADR 0002 "abrupt-replace" posture used by the `LimitedTrustBannerContainerViewController`. Pull-to-refresh transitions `.loaded` → `.loading` only when `loads.isEmpty == true` would result; otherwise the existing rows stay on screen during refresh and the `UIRefreshControl` spinner is the only visual indicator (standard iOS behavior).

## Open Question Flagged for the Planner (does not block UI-SPEC approval)

The row shows ONE counterparty verification badge (the orchestrator wording + LOAD-04 explicitly say "counterparty verification badge" — singular). For Broker → carrier, Carrier → broker, Shipper → broker, Factoring → carrier, Dispatch → broker. The **selection** of which `TrustNode` from the `ChainOfTrust` becomes that "counterparty" is a contract question — either (a) the server projects a `displayedCounterparty: TrustNode` field directly onto `LoadListEndpoint.Response.loads[]` rows, OR (b) the list response includes the abbreviated `ChainOfTrust.nodes` and the iOS view-model selects via a `RoleLoadPolicy`-style table. **(a) is preferred** because it preserves the "iOS is a passive renderer" / D-18 / LOAD-03 server-filters-fixture-side posture established by Phase 7. The planner should surface this in Phase 8's research/CONTEXT step and either confirm `(a)` with the contract owner or document the chosen approach. The UI-SPEC fixes only the *rendering* (one badge, color ramp above) — not the *selection*.
